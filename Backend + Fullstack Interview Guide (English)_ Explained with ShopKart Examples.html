Node.js Core 12 questions

1What is Node.js? What is its architecture?

What: Node.js is a JavaScript runtime that runs JS outside the browser (on the server). It is a runtime, not a language: Chrome’s V8 engine + libuv (an async I/O library) + C++ bindings + built-in modules (fs, http, crypto…).

Architecture:

Aapka JS code
   |
Node.js APIs (fs, http, crypto, stream...)
   |
C++ bindings
   |-- V8   : runs JS as machine code
   |-- libuv: event loop + thread pool + OS async I/O (epoll/kqueue/IOCP)

Why Node: best for I/O-heavy work (APIs, chat, streaming, proxies), because one thread can handle thousands of connections (non-blocking). One language (TypeScript) for frontend and backend, with code/type sharing.

When not: for CPU-heavy work (video encoding, ML, big calculations) it blocks the main thread; use worker threads / a separate service (Go, Java, Python) or a queue.

import http from "node:http";
http.createServer((req, res) => {
  res.writeHead(200, { "Content-Type": "application/json" });
  res.end(JSON.stringify({ ok: true }));
}).listen(3000);

ShopKart: the API gateway and the orders/catalog REST APIs are in Node (I/O-bound: DB + cache calls), while image resizing runs in worker threads/Lambda.

2Node.js Event Loop phases and the libuv Thread Pool

(The basic JS event loop is in the JS guide; this is the Node-specific part.)

Phases (one loop iteration):

  1. timers: callbacks of setTimeout/setInterval.
  2. pending callbacks: some system-level callbacks.
  3. idle/prepare: internal.
  4. poll: fetches new I/O events and runs their callbacks (the loop waits here if needed).
  5. check: setImmediate callbacks.
  6. close callbacks: things like socket.on("close").

After every phase (and between callbacks) the process.nextTick queue and then the Promise microtasks are drained.

libuv Thread Pool (default 4 threads, up to 128 with UV_THREADPOOL_SIZE): used for: fs (mostly), dns.lookup, crypto (pbkdf2, scrypt, randomBytes), zlib. Network I/O (sockets) does not use the thread pool; it runs on the OS’s epoll/kqueue.

const crypto = require("crypto");
for (let i = 0; i < 8; i++) {
  crypto.pbkdf2("pwd", "salt", 1e6, 64, "sha512", () => console.log(i, Date.now() - start));
}

Real insight: many parallel bcrypt/fs calls fill the pool and other fs calls wait in the queue. On a login spike, increase the pool size or use argon2 workers.

4Blocking vs Non-blocking I/O

Blocking: the thread stays stuck until the operation finishes (fs.readFileSync). All other requests of the whole server wait. Non-blocking: hand the request to the OS/libuv, the thread moves on, and a callback/promise fires when the work is done.

const data = fs.readFileSync("big.json");

// Non-blocking
const data = await fs.promises.readFile("big.json");

app.get("/report", (req, res) => {
  const out = hugeArray.sort().map(heavy);     // main thread block
  res.json(out);
});

What blocks (watch out): *Sync functions, big JSON.parse/stringify, catastrophic regex backtracking, crypto.pbkdf2Sync, big loops, big array sorts.

Fix: async APIs, streams, worker threads, split work into chunks (setImmediate), or a queue + worker service. Detect: event loop lag (perf_hooks.monitorEventLoopDelay), clinic doctor.

Require cache: a module executes the first time it is required and is cached (require.cache); later require calls return the same object. So a module-level variable acts as a singleton (a DB connection created only once).

Circular dependency: a → b → a: the second one gets a partial (incomplete) export. Fix: put shared logic in a third module, use a lazy require inside a function, or dependency injection.

In TypeScript: you write import syntax, and after compilation it becomes CJS or ESM depending on the module setting in tsconfig (NodeNext is recommended).

7Streams and Buffers

Buffer: a fixed chunk of raw binary data (bytes in memory). Stream: processing data in small chunks, without loading everything into memory.

4 types: Readable, Writable, Duplex (both), Transform (changes data in between, like gzip).

const all = await fs.promises.readFile("big.csv");

// Stream (GOOD): constant memory
import { pipeline } from "node:stream/promises";
import zlib from "node:zlib";
await pipeline(
  fs.createReadStream("big.csv"),
  zlib.createGzip(),
  fs.createWriteStream("big.csv.gz")
);

app.get("/export", (req, res) => {
  res.setHeader("Content-Type", "text/csv");
  pipeline(db.queryStream("select * from orders"), toCsvTransform(), res, err => err && console.error(err));
});

Backpressure: when the writer is slow, make the reader wait (write() returns false, wait for drain). pipeline handles this itself and destroys all streams on error (.pipe() does not). Use: file upload/download, CSV export, video streaming, proxying from S3, log processing.

8EventEmitter and Graceful Shutdown

EventEmitter: Node’s pub/sub base (http.Server, streams are all built on it).

import { EventEmitter } from "node:events";
const bus = new EventEmitter();
bus.on("order:placed", order => sendEmail(order));
bus.once("ready", () => console.log("once"));
bus.emit("order:placed", { id: 1 });

Caution: if there is no listener for the error event, the process crashes. The default limit is 10 listeners (a leak warning). Listeners run synchronously.

Graceful shutdown (essential for deployment/scale-down):

const server = app.listen(3000);

async function shutdown(signal: string) {
  console.log(signal, "received: closing new connections");
  server.close(async () => {
    await db.end();                             // DB pool band
    await redis.quit();
    process.exit(0);
  });
  setTimeout(() => process.exit(1), 10_000).unref();   // force exit safety
}
process.on("SIGTERM", () => shutdown("SIGTERM"));
process.on("SIGINT", () => shutdown("SIGINT"));

Why: without it, payments/requests in flight get cut off in a rolling deployment. In Kubernetes, fail the readiness probe to stop traffic first, then shut down.

9Error Handling in Node

Two kinds of errors:

  • Operational errors: expected runtime problems (DB down, validation failure, 404, timeout). Handle them and give the user a proper response.
  • Programmer errors: bugs (undefined.x, a wrong argument). Fix them; let the process crash (a restart manager handles it).
export class AppError extends Error {
  constructor(public statusCode: number, message: string, public code = "APP_ERROR", public isOperational = true) {
    super(message);
    Error.captureStackTrace(this, this.constructor);
  }
}
throw new AppError(404, "Product not found", "PRODUCT_NOT_FOUND");

Global safety nets:

process.on("unhandledRejection", reason => { logger.error({ reason }, "unhandledRejection"); throw reason; });
process.on("uncaughtException", err => {
  logger.fatal({ err }, "uncaughtException");
  shutdown("uncaughtException");
});

Best practices: try/catch or .catch in async code, send errors to one centralized error middleware (Q16), Error.cause, structured logging (pino), never swallow an error silently, never show a stack trace to the user, consistent error codes.

11How do you improve the performance of a Node.js application?

Checklist (measure first, then fix):

  1. Do not block the event loop: sync APIs, heavy CPU → worker threads/queue.
  2. Optimize the DB: indexes, remove N+1, select only needed columns, connection pool, pagination.
  3. Caching: Redis (hot data), HTTP cache headers, an in-memory LRU, CDN.
  4. Parallelize independent calls: Promise.all.
  5. Compression: gzip/brotli (at the reverse proxy), a smaller payload (field filtering).
  6. Scale: cluster/PM2/containers, a load balancer, stateless services.
  7. Streams for big files/exports.
  8. Keep-alive HTTP agent, DB/HTTP connection reuse.
  9. Logging: pino (fast), no sync console.log in heavy loops.
  10. Node version/updates, NODE_ENV=production.
  11. Offload: email, PDF, image work to a queue (SQS/BullMQ).

Tools: autocannon/k6 (load test), clinic.js, 0x flamegraph, node --prof, Chrome DevTools --inspect, APM (Datadog, New Relic), CloudWatch.

Real result (ShopKart): the /products API went from 800 ms to 90 ms: an index on category, a Redis cache (60 s), removing N+1 (include), Promise.all for price + stock.

12How do you find and fix Memory Leaks in Node.js?

Symptoms: RSS/heap slowly grows, GC runs again and again, finally JavaScript heap out of memory, the container is OOMKilled (exit code 137).

Common causes: global arrays/Maps that keep growing (an unbounded cache), event listeners that are not removed (MaxListenersExceededWarning), big objects in closures, uncleared timers/intervals, holding request objects globally, big in-memory sessions.

Debug steps:

  1. Confirm: the process.memoryUsage() / CloudWatch metrics trend.
  2. Run with the inspector: node --inspect server.js → Chrome chrome://inspect → Memory tab → Heap snapshots (before and after load; in the Comparison view see what is growing).
  3. Heap profiling in production: heapdump/v8.writeHeapSnapshot(), the Clinic.js heapprofiler.
  4. Look at the retainers: what reference is keeping the object alive.
  5. Fix + verify with a load test.
app.get("/x", (req, res) => { bus.on("tick", () => res.write("t")); });

// Fix
app.get("/x", (req, res) => {
  const h = () => res.write("t");
  bus.on("tick", h);
  req.on("close", () => bus.off("tick", h));
});

// Unbounded cache -> LRU (max size)

A temporary guard: --max-old-space-size, container memory limits + restart, but fix the root cause.

Express.js 12 questions

13What is Express.js? The Request-Response lifecycle

What: a minimal web framework on top of Node: routing + a middleware chain. A comfortable wrapper over Node’s raw http module.

import express from "express";
const app = express();

app.use(express.json());                              // body parser middleware

app.get("/api/products/:id", async (req, res) => {
  const product = await productService.getById(req.params.id);
  res.status(200).json(product);
});

app.listen(3000, () => console.log("up"));

Lifecycle:

Client -> [Global middlewares: logger, cors, helmet, json parser]
       -> [Route match: method + path]
       -> [Route middlewares: auth, validate]
       -> [Controller handler -> service -> DB]
       -> res.json()  (response bheja)
       -> (on error) -> [Error-handling middleware]

Key objects: req (params, query, body, headers, cookies), res (status, json, send, redirect, set). Every request must get exactly one response (sending twice gives “Cannot set headers after they are sent”).

14What is Middleware? How many types, and why does order matter?

What: a function (req, res, next) that runs between the request and response; it can modify the request, send a response, or hand control to the next with next().

const logger: RequestHandler = (req, res, next) => {
  const start = Date.now();
  res.on("finish", () => console.log(req.method, req.originalUrl, res.statusCode, Date.now() - start, "ms"));
  next();
};
app.use(logger);                      // application-level
app.use("/admin", authenticate, authorize("admin"), adminRouter);   // path + route-level

Types: application-level (app.use), router-level, built-in (express.json, static), third-party (cors, helmet, morgan), error-handling (4 args), route-specific.

Order matters: they run top to bottom.

app.use(helmet());
app.use(cors({ origin: config.CLIENT_URL, credentials: true }));
app.use(express.json({ limit: "1mb" }));
app.use(requestId, logger);
app.use("/api", apiRouter);           // routes
app.use(notFound);                    // 404
app.use(errorHandler);

Mistakes: forgetting next() (the request hangs), sending a response after next(), placing the error middleware before the routes, reading req.body before the body parser.

16Error-handling Middleware and Async Errors

A middleware with 4 arguments is the error handler. Register it last.

export const errorHandler: ErrorRequestHandler = (err, req, res, next) => {
  const status = err instanceof AppError ? err.statusCode : 500;
  if (status >= 500) logger.error({ err, reqId: req.id }, "unhandled");
  res.status(status).json({
    error: { code: err.code ?? "INTERNAL_ERROR",
             message: status === 500 ? "Something went wrong" : err.message },
  });
};

Async errors:

  • Express 4: the rejected promise of an async handler does not automatically go to next(err); the request hangs/the process crashes. Fix: a wrapper or express-async-errors.
const asyncHandler = (fn: RequestHandler): RequestHandler => (req, res, next) =>
  Promise.resolve(fn(req, res, next)).catch(next);
router.get("/:id", asyncHandler(async (req, res) => { res.json(await svc.get(req.params.id)); }));
  • Express 5: rejected promises/async errors go to the error middleware automatically; no wrapper needed.

Pattern: the business layer throws an AppError, and the HTTP response is built in one place (the error middleware). Validation errors 400/422, auth 401/403, not found 404.

19Request Validation (Zod / Joi)

Why: never trust the client. Stop wrong/malicious input before it reaches the DB.

import { z } from "zod";

export const createProductSchema = z.object({
  body: z.object({
    name: z.string().min(2).max(120),
    price: z.number().positive(),
    category: z.enum(["shoes", "bags", "watches"]),
    tags: z.array(z.string()).max(10).default([]),
  }),
});
export type CreateProductInput = z.infer<typeof createProductSchema>["body"];

export const validate = (schema: z.ZodTypeAny): RequestHandler => (req, res, next) => {
  const result = schema.safeParse({ body: req.body, query: req.query, params: req.params });
  if (!result.success) {
    return res.status(400).json({ error: { code: "VALIDATION", details: result.error.flatten() } });
  }
  Object.assign(req, result.data);      // typed + cleaned data
  next();
};

router.post("/", validate(createProductSchema), createProduct);

Best practices: whitelist (strip extra fields), coerce types (z.coerce.number() for query), user-friendly messages, a TypeScript type from the same schema (Q42), and you can share it with the frontend. To avoid mass assignment, never pass req.body straight to Model.create(req.body).

20JWT Authentication + Authorization (RBAC) in Express: the full flow
// auth.service.ts
const ACCESS_TTL = "15m", REFRESH_TTL_DAYS = 7;

export async function login(email: string, password: string) {
  const user = await userRepo.findByEmail(email);
  const ok = user && (await bcrypt.compare(password, user.passwordHash));
  if (!ok) throw new AppError(401, "Invalid email or password", "INVALID_CREDENTIALS");

  const accessToken = jwt.sign({ sub: user.id, role: user.role }, config.JWT_SECRET, { expiresIn: ACCESS_TTL });
  const refreshToken = crypto.randomBytes(48).toString("hex");
  await refreshRepo.save({ userId: user.id, tokenHash: sha256(refreshToken), expiresAt: addDays(REFRESH_TTL_DAYS) });
  return { accessToken, refreshToken, user: publicUser(user) };
}

res.cookie("rt", refreshToken, { httpOnly: true, secure: true, sameSite: "strict", maxAge: 7 * 864e5, path: "/api/auth" });
res.json({ accessToken });

// middleware
export const authenticate: RequestHandler = (req, res, next) => {
  const token = req.headers.authorization?.split(" ")[1];
  if (!token) return next(new AppError(401, "Token missing"));
  try {
    const payload = jwt.verify(token, config.JWT_SECRET) as { sub: string; role: Role };
    req.user = { id: payload.sub, role: payload.role };
    next();
  } catch { next(new AppError(401, "Token invalid or expired")); }
};

export const authorize = (...roles: Role[]): RequestHandler => (req, res, next) =>
  roles.includes(req.user!.role) ? next() : next(new AppError(403, "Permission denied"));

Refresh endpoint: match the cookie’s token hash in the DB, rotate (invalidate the old one, issue a new one), and on reuse revoke the whole family (a sign of token theft). Logout: revoke the refresh token + clear the cookie. 401 vs 403: 401 = identity unknown (log in), 403 = identity known but no permission. The frontend flow and token storage are in the React guide’s Authentication section.

// GET /api/products?category=shoes&minPrice=500&sort=-price&page=2&limit=20
const querySchema = z.object({

  minPrice: z.coerce.number().optional(),
  sort: z.enum(["price", "-price", "createdAt", "-createdAt"]).default("-createdAt"),
  page: z.coerce.number().int().min(1).default(1),
  limit: z.coerce.number().int().min(1).max(100).default(20),

25What is REST? HTTP methods, idempotency, PUT vs PATCH

What: REST (Representational State Transfer) is an architectural style: represent resources (nouns) with URLs, operate on them with HTTP methods, and keep requests stateless.

Principles: client-server, stateless (each request carries all the info), cacheable, uniform interface, layered system.

30CORS: how does it work internally?

Problem: the browser’s Same-Origin Policy stops JS from reading a response from another origin (domain+port+protocol). CORS is the server’s way of telling the browser “this origin is allowed.”

Frontend: https://shopkart.com  ->  API: https://api.shopkart.com   (alag origin)

Simple request (GET/POST with basic headers): the browser sends an Origin header; the server answers with Access-Control-Allow-Origin.

Preflight: before a non-simple request (PUT/DELETE, an Authorization header, a JSON content-type) the browser sends an OPTIONS request: “may I use this method/these headers?”

app.use(cors({
  origin: ["https://shopkart.com", "https://admin.shopkart.com"],
  methods: ["GET", "POST", "PATCH", "DELETE"],
  allowedHeaders: ["Content-Type", "Authorization"],
  credentials: true,                  // cookies allow
  maxAge: 600,                        // preflight cache
}));

Remember: CORS does not apply to server-to-server (curl/Postman); it is purely a browser rule. CORS is not a security feature that protects an API (an attacker can call with curl); authentication is the real protection. The error “No Access-Control-Allow-Origin” = a server config issue, not a frontend fix.

31Idempotency Key: so a payment is not charged twice

Problem: the user pressed “Pay”, the network timed out, and the client retried. Without protection, a double payment.

Solution: for every logical operation the client sends a unique Idempotency-Key (UUID); the server does the work the first time and stores the result, and on the same key returns that same result.

router.post("/payments", authenticate, async (req, res) => {
  const key = req.header("Idempotency-Key");
  if (!key) return res.status(400).json({ error: { code: "KEY_REQUIRED" } });

  const cacheKey = `idem:${req.user!.id}:${key}`;
  const claimed = await redis.set(cacheKey, "IN_PROGRESS", { NX: true, EX: 86400 });   // atomic claim
  if (!claimed) {
    const saved = await redis.get(cacheKey);
    if (saved === "IN_PROGRESS") return res.status(409).json({ error: { code: "IN_PROGRESS" } });
    const { status, body } = JSON.parse(saved!);
    return res.status(status).json(body);
  }

  try {
    const payment = await paymentService.charge(req.user!.id, req.body);
    const body = { id: payment.id, status: payment.status };
    await redis.set(cacheKey, JSON.stringify({ status: 201, body }), { EX: 86400 });
    res.status(201).json(body);
  } catch (e) { await redis.del(cacheKey); throw e; }
});

DB-level safety: a UNIQUE constraint on orders.idempotency_key (no duplicates even in a race). Stripe/Razorpay work on this pattern. Retries (Q71) are safe only when the operation is idempotent.

45Indexes: how they work and when to add them

What: a separate sorted structure (mostly a B-tree) on table column(s) that makes search O(log n) instead of an O(n) full table scan.

CREATE INDEX idx_products_category ON products(category);
CREATE UNIQUE INDEX idx_users_email ON users(email);
CREATE INDEX idx_orders_user_created ON orders(user_id, created_at DESC);   -- composite

Composite index rule (leftmost prefix): an index on (user_id, created_at) helps in WHERE user_id = ? and WHERE user_id = ? AND created_at > ?, but not in only WHERE created_at > ?. Order: equality columns first, range/sort after.

When to add: columns in WHERE, JOIN (foreign keys), ORDER BY, GROUP BY, and high selectivity (few duplicates).

When not / costs: every index slows writes (INSERT/UPDATE/DELETE) and takes storage. Small tables, low-cardinality columns (gender, isActive), columns that are rarely queried.

When an index is not used: WHERE LOWER(email) = ... (a function applied), LIKE '%abc' (a leading wildcard), a type mismatch, OR in some cases, a very unselective filter.

Types: B-tree (default), Hash, GIN (JSONB/full-text/arrays), Partial index (WHERE deleted_at IS NULL), Covering index (INCLUDE), Unique. Clustered vs non-clustered: in MySQL InnoDB the primary key is clustered (data is stored in that order). Always verify with EXPLAIN (Q49).

  • 3NF: 2NF + no transitive dependency (a non-key column depends only on the key, not on another non-key).
Wrong: orders(id, user_id, user_name, user_city, product_name, ...)   -> user_name duplicated, update anomaly
Right: users(id, name, city)  orders(id, user_id)  order_items(order_id, product_id, qty)  products(id, name, price)

Benefits: less storage, consistent updates. Drawbacks: more joins (reads are slower).

Denormalization: deliberately keeping duplicate/precomputed data for read speed (e.g. orders.total, products.review_count, a price snapshot of the product in the order).

Rule: normalize by default (3NF), denormalize where reads are a measured bottleneck, and have a plan to keep the duplicate data consistent (triggers/events/jobs). Always keep a price snapshot: if a product’s price changes later, old orders must not change.

48The N+1 Query Problem

Problem: one query fetches the list, then a separate query for every item (N queries). 100 orders = 101 queries.

  o.user = await prisma.user.findUnique({ where: { id: o.userId } });   // N
}

// Fix 1: eager loading / join

// Fix 2: batch with IN

Detect: query logging (log: ["query"]), APM, the DB slow-query log, a “queries per request” metric. Real (ShopKart): the orders page took 3 s (1 + 200 queries); with include it took 120 ms.

49Query Optimization and EXPLAIN

Process: catch the slow query (slow query log, APM) → EXPLAIN ANALYZE → see the bottleneck → fix → measure again.

  • Seq Scan (the whole table) on a big table = a missing index. Index Scan / Index Only Scan = good.
  • A big gap between estimated and actual rows = stale statistics (ANALYZE).
  • A Sort/Hash step that spills to disk.
  • Cost and actual time.

  1. The right (composite/partial) index.
  2. Only the needed columns instead of SELECT *.
  3. Pagination (LIMIT + keyset), avoid big OFFSET.
  4. Remove N+1, joins/batching.
  5. Do not wrap an indexed column in a function.
  6. Test EXISTS vs IN vs join; CTE/join instead of a subquery.
  7. For heavy aggregation: a materialized view / pre-aggregation / a read replica.
  8. Cache (Redis) for hot reads.
  9. Table partitioning (very big tables), archive old data.
  10. Connection pooling (Q50).
50Connection Pooling

Problem: making a new DB connection per request is slow (TCP + TLS + auth) and DB connections are limited (Postgres default ~100). Too many connections waste memory/CPU.

Solution: a pool of a few ready connections; a request takes one from the pool, does its work, and returns it.

import { Pool } from "pg";
export const pool = new Pool({
  connectionString: config.DATABASE_URL,
  max: 20,                       // pool size
  idleTimeoutMillis: 30_000,
  connectionTimeoutMillis: 2_000,
});
const { rows } = await pool.query("SELECT * FROM products WHERE id = $1", [id]);   // auto acquire/release

const client = await pool.connect();
try { await client.query("BEGIN"); /* ... */ await client.query("COMMIT"); }
catch (e) { await client.query("ROLLBACK"); throw e; }
finally { client.release(); }          // release bhoolna = pool leak

Pool size: too big overloads the DB, too small makes requests wait. Instances x pool size < the DB max connections. The serverless (Lambda) issue: every concurrent Lambda creates its own pool → connections run out. Fix: RDS Proxy, PgBouncer, or a serverless-friendly DB (DynamoDB, Aurora Data API). Call pool.end() in graceful shutdown.

54Optimistic vs Pessimistic Locking (the inventory oversell problem)

Problem: stock is 1 and two users order at the same time. Both check “stock = 1” and both create an order → oversell (a race condition).

1. An atomic conditional update (the simplest, the best):

UPDATE products SET stock = stock - 1 WHERE id = 42 AND stock >= 1;   -- affected rows 0 = out of stock

2. Pessimistic locking: lock the row until the transaction ends.

BEGIN;
SELECT stock FROM products WHERE id = 42 FOR UPDATE;
-- check, update
COMMIT;

3. Optimistic locking: no lock; check a version.

const updated = await prisma.product.updateMany({

  data: { stock: current.stock - 1, version: { increment: 1 } },
});

55Replication, Sharding and Partitioning
  • Replication: copies of data. Primary (writes) + Read replicas (reads). Read scale + high availability (failover). Replication lag → a replica can return stale data (read critical data from the primary for read-your-writes).
  • Partitioning: splitting one big table into smaller parts (by date/hash/range) on the same server → faster queries/maintenance.
  • Sharding: splitting data across different servers (horizontal scale). The shard key is important.
Sharding: user_id % 4 -> shard0..shard3

Choosing the shard key: high cardinality, even distribution (so no hot shard), used often in queries. Bad keys: country (one country is huge), created_at (new data all lands on one shard).

Problems: cross-shard joins/transactions, resharding, hot spots. So first vertical scale + indexes + cache + read replicas; sharding is a last resort. Consistent hashing (A1) makes resharding less painful. Managed: Aurora (replicas), DynamoDB/Cosmos (auto partition), a Mongo sharded cluster.

56CAP Theorem and Consistency Models

CAP: in a distributed system, when a network partition (P) happens you must choose between Consistency (C) and Availability (A) (you cannot have both). Partitions do happen in real life, so the practical choice is: CP or AP.

  • CP: consistency first; during a partition some requests are rejected (banking, inventory), e.g. HBase, Mongo (primary reads by default), Zookeeper.
  • AP: availability first; may serve stale data and sync later (eventual consistency), e.g. Cassandra, DynamoDB (eventual), DNS.

Consistency models: Strong (a read always returns the latest), Eventual (all replicas become the same after some time), Read-your-writes, Causal.

BASE (the NoSQL approach): Basically Available, Soft state, Eventually consistent, in contrast to ACID.

Real: cart/likes/view counts can be eventual. Payments/stock need strong. DynamoDB has a ConsistentRead: true option (costs more). PACELC: even without a partition there is a Latency vs Consistency trade-off.

Problems:

  • Invalidation: “one of the two hard problems in computer science.” TTL + delete/update on write.
  • Cache stampede (thundering herd): when a popular key expires, thousands of requests hit the DB. Fix: a lock/single-flight (only one request goes to the DB), TTL jitter, stale-while-revalidate, background refresh.
  • Cache penetration: repeated requests for non-existent keys (hitting the DB). Fix: cache nulls with a short TTL, a Bloom filter (A2).
  • Cache avalanche: many keys expiring together → randomize TTLs.
  • Hot key, stale data, memory eviction.

What to cache: read-heavy, rarely changing, expensive data (product details, categories). What not: personal sensitive data, data that changes every time.

Attack:

60Migrations, Soft Delete and Zero-Downtime Schema Changes

Migrations: keep schema changes in version-controlled files (Prisma Migrate, Knex, Flyway, Liquibase). The same sequence in every environment. Have a rollback plan.

-- 001_add_phone.sql
ALTER TABLE users ADD COLUMN phone TEXT;

Zero-downtime (the expand/contract pattern): do not rename a column in one step:

  1. Expand: add the new column (nullable), the app writes to both.
  2. Backfill: copy the old data into the new one (in batches).
  3. Switch: the app reads from the new column.
  4. Contract: drop the old column later.

Dangerous operations: ALTER on a big table (lock), NOT NULL + default (a rewrite in older DBs), use CREATE INDEX CONCURRENTLY (Postgres) for indexes.

Soft delete: a deleted_at timestamp; do not remove the row. Benefit: recover, audit. Drawback: WHERE deleted_at IS NULL in every query (a partial index, ORM middleware/global filter), watch unique constraints, and GDPR also needs a hard delete.

Seed/test data: separate seed scripts; do not bring production data to local (PII).

63Password Hashing: bcrypt, argon2, salt

Rule: a password is never plain text or a fast hash (MD5/SHA256). Use a slow, salted, adaptive hash.

  • Hashing (one-way) vs Encryption (two-way): a password is never decrypted, only matched.
  • Salt: a random value per password; the same password gets a different hash (rainbow tables fail).
  • Cost factor: the hash is deliberately slow (brute force becomes costly).
import bcrypt from "bcrypt";
const hash = await bcrypt.hash(password, 12);
const ok = await bcrypt.compare(password, hash);         // timing-safe

import argon2 from "argon2";                              // newer, recommended (memory-hard)
const h = await argon2.hash(password);  await argon2.verify(h, password);

Best practices: cost 10-12+ (raise it with hardware), argon2id or bcrypt/scrypt, a password policy (length over complexity), a breached-password check, rate limit/lockout, MFA, use async bcrypt (sync blocks the event loop), reset tokens short-lived + single use + stored hashed, the same error message “invalid email or password” (prevents user enumeration). bcrypt has a 72-byte limit and uses the thread pool (Q2).

  • RBAC (Role-Based): User → Role → Permissions. Simple: admin, seller, customer.
  • ABAC (Attribute-Based): rules on attributes (user.department == resource.department AND time < 6pm). More flexible, more complex.
  • Resource ownership: a user only touches their own things.

71Resilience Patterns: Timeout, Retry, Circuit Breaker, Bulkhead

In a distributed system downstream services fail. If your code waits blindly, you get a cascading failure.

  1. Timeout: on every outbound call (HTTP, DB). Without a timeout a request hangs forever.
  2. Retry with exponential backoff + jitter: only for idempotent/transient errors (the JS guide’s retry polyfill). Avoid a retry storm (max attempts).
  3. Circuit Breaker: if a downstream keeps failing, stop calling it for a while (fail fast), then test.
CLOSED (normal) --failures > threshold--> OPEN (fail fast, no calls) --timeout--> HALF-OPEN (a few test calls)
     ^------------------------ success ------------------------------------------------|

import CircuitBreaker from "opossum";
const breaker = new CircuitBreaker(callPaymentApi, { timeout: 3000, errorThresholdPercentage: 50, resetTimeout: 10_000 });
breaker.fallback(() => ({ status: "PENDING", note: "Will retry later" }));
const result = await breaker.fire(payload);
  1. Bulkhead: separate resources (a separate pool/queue) so one dependency cannot consume everything.
  2. Fallback / graceful degradation: if the recommendation service is down, show default products and do not stop checkout.
  3. Rate limiting & load shedding: reject some requests under overload.
  4. Health checks, idempotency (Q31).

ShopKart: a slow payment gateway → a 3 s timeout + a circuit breaker; mark the order “PENDING” and confirm later through a queue.

72Distributed Transactions: Saga and Outbox Pattern

Problem: in microservices, Order, Payment and Inventory have separate DBs. One ACID transaction cannot span them all (2PC is heavy/fragile).

Saga: a chain of local transactions; on failure, compensating actions (undo).

Order Service: create order (PENDING)
  -> Payment: charge          (fail?) -> Order: CANCELLED
  -> Inventory: reserve       (fail?) -> Payment: REFUND -> Order: CANCELLED
  -> Order: CONFIRMED
  • Choreography: services trigger each other through events (decentralized, simple, hard to trace).
  • Orchestration: an orchestrator controls the steps (AWS Step Functions, Temporal): a clear flow, centralized.

Outbox pattern (the dual-write problem): “save to DB + publish a message” is not atomic (the DB save succeeds but the publish fails). Fix: in the same DB transaction write the event into an outbox table, and a separate relay process publishes it to the queue.

BEGIN;
INSERT INTO orders (...);
INSERT INTO outbox (event_type, payload) VALUES ('OrderPlaced', '{...}');
COMMIT;

Rules: make consumers idempotent, accept eventual consistency, design the compensations, and keep a clear state machine (the order status).

74System Design: URL Shortener (bit.ly)

Requirements: long URL → short code; redirect; (optional) analytics, expiry, custom alias. Read-heavy (100:1). Scale: 100M URLs, ~1000 redirects/sec.

API:

POST /api/shorten  { longUrl, expiresAt? } -> { shortUrl: "https://sho.rt/aZ3kP9x" }
GET  /:code        -> 302 redirect to longUrl

How to generate the short code:

  1. Counter + Base62 (A5): encode a unique ID (a DB sequence / distributed ID generator) in base62. 7 chars = 62^7 ~ 3.5 trillion. No collisions, predictable (shuffle/salt for security).
  2. The first 7 chars of a hash (MD5/SHA): collisions must be handled.
  3. A random code + a unique constraint, retry on conflict.

Architecture:

Client -> CDN/LB -> API servers (stateless)
                      |-> Redis cache (code -> longUrl, TTL)  <- 95% of reads served from here
                      |-> DB (code PK, longUrl, createdAt, expiresAt)  [Postgres / DynamoDB, key-value access]
                      |-> Queue -> Analytics worker (click counts, geo) -> OLAP store

Decisions: 301 vs 302: a 301 is cached by the browser (analytics are missed), a 302 hits the server each time. Cache-aside + LRU. Partition the DB by code hash. Rate limit (abuse), URL validation/malware check. ID generation must not be a single point of failure (range allocation per server / snowflake). Estimation: 100M x 500B = 50GB, fits easily. In an interview, first state requirements and numbers, then the high level, then a deep dive.

75System Design: ShopKart Checkout and Flash Sale (Inventory)

Challenge: the moment a sale starts, 100k users hit at once and stock is only 500. No overselling, no crash, money safe.

Flow:

User -> CDN (static) -> API Gateway (rate limit, waiting room)
 -> Order API:
     1. Redis atomic: DECR stock:p42  (reserve if >= 0, else "Sold out" immediately)
     2. Reservation create (TTL 10 min) + order PENDING (DB, idempotency key)
     3. Queue (SQS) -> Payment worker
 -> Payment gateway (timeout + circuit breaker)
 -> Success: order CONFIRMED, DB stock final, email event
    Fail/timeout: reservation release -> Redis INCR

const left = await redis.decr(`stock:${productId}`);
if (left < 0) { await redis.incr(`stock:${productId}`); throw new AppError(409, "Sold out"); }

Key points:

  • A Redis atomic counter as the front gate (protects the DB), a conditional update in the DB (Q54) as the final truth.
  • A reservation with a TTL (cart hold); on expiry the stock returns.
  • A queue absorbs the spike, payment is async, idempotency (Q31).
  • Rate limiting + a virtual waiting room, bot protection (CAPTCHA/WAF).
  • Read path cache/CDN, DB read replicas.
  • Saga (Q72) compensates on failure, events through the outbox.
  • Monitoring: queue depth, error rate, a stock mismatch reconciliation job.

State the trade-off: inconsistency between Redis and the DB (if Redis crashes) → a reconciliation job; strong consistency vs speed.

81How do you debug a Production Issue? (Step by step)

JD: “Good debugging skills to identify bottlenecks, production issues.”

Framework:

  1. Stabilize first: reduce user impact (rollback, turn off a feature flag, scale up, shift traffic). Root cause later.
  2. Understand the scope: what broke? Since when? How many users? Which service/region? Was there a deploy or config change? (the most common reason).
  3. Look at the signals: dashboards (error rate, latency, CPU/memory, DB connections, queue depth), logs (trace with the request ID), distributed traces, recent deployments.
  4. Hypothesis → test: one by one (DB slow? downstream timeout? memory leak? bad deploy? traffic spike?).
  5. Reproduce (staging/local), a debugger/profiler.
  6. Fix + verify (metrics normal), hotfix vs a proper fix.
  7. Postmortem (blameless): timeline, root cause, 5 whys, action items (alert, test, runbook).

89Lambda Cold Start, Concurrency and Limits

Cold start: creating a new execution environment: container start → runtime init → your init code (imports, clients) → handler. The first request (or one after idle) is slow (Node: ~100-500 ms typically; more for Java/.NET, and VPC/big packages make it worse). Warm invocation: the old environment is reused → fast.

Ways to reduce it:

  • A small bundle (esbuild, no unused deps), lazy imports (import a heavy library only when needed).
  • Provisioned Concurrency (pre-warmed instances; paid).
  • SnapStart (Java), ARM64 (Graviton, cheaper/faster), more memory (more CPU).
  • No heavy work in init; a modular SDK v3.
  • For latency-critical paths consider a container (Fargate/ECS) instead of Lambda.

Concurrency:

  • Concurrent executions = instances running at one time. Every concurrent request = a separate environment.
  • Account limit (default 1000/region). Reserved concurrency: guaranteed + an upper cap for a function (to protect a downstream DB). Provisioned: pre-warmed.
  • Past the limit you get throttling (429); sync callers get an error, async/SQS retry.

DB connections issue: 1000 concurrent Lambdas = 1000 DB connections. Fix: RDS Proxy, a reserved concurrency cap, DynamoDB.

Retries: async invocations retry 2 times, an SQS trigger uses the visibility timeout + DLQ, stream sources retry until the data expires. Idempotency is essential.

93DynamoDB: Partition key, Sort key, GSI, Capacity and Single-table design

Basics: each item’s primary key in a table = the Partition key (PK) (+ an optional Sort key (SK)). The hash of the PK decides which partition the item goes to. Design keys according to the access patterns.

// Item
{ pk: "USER#42", sk: "ORDER#2025-06-01#9001", total: 2999, status: "PAID" }

await ddb.send(new QueryCommand({
  TableName: T, KeyConditionExpression: "pk = :p AND begins_with(sk, :o)",
  ExpressionAttributeValues: { ":p": "USER#42", ":o": "ORDER#" }, ScanIndexForward: false, Limit: 20,
}));

Query vs Scan: Query works by key (fast, cheap). Scan reads the whole table (slow/costly, avoid).

Indexes: GSI (Global Secondary Index): another PK/SK for a second access pattern (e.g. status + createdAt); eventually consistent. LSI: the same PK, a different SK (only at table creation).

Capacity modes: On-demand (pay per request, spiky) / Provisioned (+ auto scaling, predictable). Hot partition problem: too much traffic on one PK → throttling; choose a high-cardinality PK.

Other: TTL (auto-expire items, sessions), Streams (change events → Lambda), conditional writes (ConditionExpression: optimistic locking/idempotency), Transactions, DAX (cache), a 400KB item max, single-table design (different entity types in one table, for access patterns).

99What is CI/CD? Pipeline stages

CI (Continuous Integration): an automatic build + test + lint on every code push/PR so integration bugs are caught early. CD: Continuous Delivery (a deploy-ready artifact, manual approval) / Continuous Deployment (automatic all the way to production).

Push/PR -> [Install (npm ci)] -> [Lint + Type-check] -> [Unit tests + coverage]

        -> [Docker build + push to ECR] -> [Deploy to staging] -> [Smoke/E2E tests]
        -> [Manual approval] -> [Deploy to production] -> [Health check / rollback]

Benefits: fast feedback, fewer manual errors, repeatable releases, small frequent deployments (less risk).

Best practices: pipeline as code (YAML, version-controlled), build once, deploy the same artifact everywhere, environment-specific config kept separate, secrets in the CI secret store, caching (node_modules), parallel jobs, branch protection (a mandatory PR + checks), a fast pipeline (<10 min), fix flaky tests. D1Big-O (Time/Space Complexity) and a Problem-solving approach

Big-O: how running time/memory grows as the input size n grows (worst case, growth rate).

Big-O Name Example
O(1) Constant Array index, Map get/set
O(log n) Logarithmic Binary search, a balanced BST, heap push
O(n) Linear One loop, linear search
O(n log n) Linearithmic Merge sort, sort()
O(n^2) Quadratic Nested loops, bubble sort
O(2^n) Exponential Naive recursion (fib), subsets

Rules: drop constants (2n → n), keep the dominant term (n^2 + n → n^2). Space = extra memory (the recursion stack counts too). Amortized: array.push is O(1) on average (it occasionally resizes).

Built-in costs in JS: arr.push/pop O(1), shift/unshift O(n), includes/indexOf O(n), Map/Set get/has/add O(1) average, sort O(n log n), slice/concat/spread O(n), string concatenation in loops is costly, arr.splice O(n).

A problem-solving framework (say it aloud in the interview):

  1. Understand: input/output, constraints (how big is n? → n=10^5 means up to O(n log n)), edge cases (empty, duplicates, negative).
  2. State the brute force (O(n^2)) and its complexity.
  3. Recognize the pattern: hashing? two pointers? sliding window? sorting + binary search? stack? BFS/DFS? DP? heap?
  4. Optimize, with the trade-off (space for time).
  5. Code (clean names), dry run, test edge cases, state the complexity.

Hints from constraints: n <= 20 → backtracking/bitmask; n <= 10^3 → O(n^2); n <= 10^5 → O(n log n)/O(n); n <= 10^9 → O(log n)/math.

D2Two Sum (the Hashing pattern)

Problem: find two numbers in an array whose sum is target; return their indices.

Brute force: two loops, O(n^2). Optimal: one pass, a Map of value -> index. For each number, have we seen target - num before?

function twoSum(nums, target) {
  const seen = new Map();                         // value -> index
  for (let i = 0; i < nums.length; i++) {
    const need = target - nums[i];
    if (seen.has(need)) return [seen.get(need), i];
    seen.set(nums[i], i);
  }
  return [];
}
twoSum([2, 7, 11, 15], 9);   // [0, 1]

Complexity: Time O(n), Space O(n). Pattern: “have I seen this before?” = HashMap/Set (duplicates, pairs, frequency). Variations: two pointers on a sorted array (D4, O(1) space), 3Sum (sort + two pointers, O(n^2)), count pairs.

D3Valid Anagram and Group Anagrams (Frequency counting)
// Valid anagram: O(n) time
function isAnagram(a, b) {
  if (a.length !== b.length) return false;
  const count = new Map();
  for (const c of a) count.set(c, (count.get(c) ?? 0) + 1);
  for (const c of b) {
    if (!count.get(c)) return false;
    count.set(c, count.get(c) - 1);
  }
  return true;
}

function groupAnagrams(words) {
  const groups = new Map();
  for (const w of words) {
    const key = [...w].sort().join("");                    // O(k log k)
    // faster key: 26-letter count array -> counts.join("#")
    if (!groups.has(key)) groups.set(key, []);
    groups.get(key).push(w);
  }
  return [...groups.values()];
}
groupAnagrams(["eat", "tea", "tan", "ate", "nat", "bat"]);
// [["eat","tea","ate"],["tan","nat"],["bat"]]

Complexity: Group: O(n * k log k) (k = word length). Pattern: canonical form / frequency map. Real use: duplicate detection, search suggestions.

D4Two Pointers: Valid Palindrome, Container With Most Water, 3Sum

Idea: turn O(n^2) into O(n) with two pointers (start/end or slow/fast), mostly on sorted/linear structures.

// 1. Palindrome (alphanumeric, case ignore)
function isPalindrome(s) {
  let l = 0, r = s.length - 1;
  const ok = c => /[a-z0-9]/i.test(c);
  while (l < r) {
    if (!ok(s[l])) { l++; continue; }
    if (!ok(s[r])) { r--; continue; }
    if (s[l].toLowerCase() !== s[r].toLowerCase()) return false;
    l++; r--;
  }
  return true;
}

// 2. Container with most water (heights array)
function maxArea(h) {
  let l = 0, r = h.length - 1, best = 0;
  while (l < r) {
    best = Math.max(best, Math.min(h[l], h[r]) * (r - l));
    h[l] < h[r] ? l++ : r--;
  }
  return best;
}

// 3. 3Sum (sort + two pointers) O(n^2), duplicates skip
function threeSum(nums) {
  nums.sort((a, b) => a - b);
  const res = [];
  for (let i = 0; i < nums.length - 2; i++) {
    if (i > 0 && nums[i] === nums[i - 1]) continue;
    let l = i + 1, r = nums.length - 1;
    while (l < r) {
      const sum = nums[i] + nums[l] + nums[r];
      if (sum === 0) {
        res.push([nums[i], nums[l], nums[r]]);
        while (nums[l] === nums[l + 1]) l++;
        while (nums[r] === nums[r - 1]) r--;
        l++; r--;
      } else sum < 0 ? l++ : r--;
    }
  }
  return res;
}

Also: remove duplicates in place (slow/fast), move zeroes, merge sorted arrays, linked list cycle (D9). Time O(n) (3Sum O(n^2)), Space O(1).

D5Sliding Window: Longest Substring without Repeating, Max Sum Subarray of size K

Idea: a window (a contiguous subarray/substring) that moves forward; at each step add the new element and remove the old, without recomputing. When: “contiguous subarray/substring”, “longest/shortest with a condition”, “size k”.

// Longest substring without repeating chars: O(n)
function lengthOfLongestSubstring(s) {
  const last = new Map();                        // char -> last index
  let start = 0, best = 0;
  for (let i = 0; i < s.length; i++) {
    const c = s[i];
    if (last.has(c) && last.get(c) >= start) start = last.get(c) + 1;   // window shrink
    last.set(c, i);
    best = Math.max(best, i - start + 1);
  }
  return best;
}
lengthOfLongestSubstring("abcabcbb");   // 3

// Max sum of subarray of fixed size k
function maxSumK(nums, k) {
  let sum = 0;
  for (let i = 0; i < k; i++) sum += nums[i];
  let best = sum;
  for (let i = k; i < nums.length; i++) {
    sum += nums[i] - nums[i - k];
    best = Math.max(best, sum);
  }
  return best;
}

// Smallest subarray with sum >= target (variable window)
function minSubArrayLen(target, nums) {
  let l = 0, sum = 0, best = Infinity;
  for (let r = 0; r < nums.length; r++) {
    sum += nums[r];

  return best === Infinity ? 0 : best;
}

D7Binary Search (and variations)

Idea: in sorted (or monotonic) data, halve the search space at every step: O(log n).

function binarySearch(arr, target) {
  let lo = 0, hi = arr.length - 1;
  while (lo <= hi) {
    const mid = lo + Math.floor((hi - lo) / 2);   // overflow-safe style
    if (arr[mid] === target) return mid;
    arr[mid] < target ? (lo = mid + 1) : (hi = mid - 1);
  }
  return -1;
}

function lowerBound(arr, target) {
  let lo = 0, hi = arr.length;
  while (lo < hi) {
    const mid = (lo + hi) >> 1;
    arr[mid] < target ? (lo = mid + 1) : (hi = mid);
  }
  return lo;
}

function searchRotated(nums, target) {
  let lo = 0, hi = nums.length - 1;
  while (lo <= hi) {
    const mid = (lo + hi) >> 1;
    if (nums[mid] === target) return mid;
    if (nums[lo] <= nums[mid]) {                                   // left half sorted
      target >= nums[lo] && target < nums[mid] ? (hi = mid - 1) : (lo = mid + 1);
    } else {                                                       // right half sorted
      target > nums[mid] && target <= nums[hi] ? (lo = mid + 1) : (hi = mid - 1);
    }
  }
  return -1;
}

“Binary search on the answer”: when the answer is monotonic (e.g. the minimum capacity so packages ship in D days), binary search over the answer range lo..hi + a feasibility check. Real use: DB indexes (B-tree), git bisect, sorted pagination, first bad version.

D16Heap / Priority Queue: Top K Frequent Elements, Kth Largest

Heap: a complete binary tree where parent <= children (min-heap). push/pop O(log n), peek O(1). JS has no built-in one, so write your own (in the interview too).

class MinHeap {
  constructor(cmp = (a, b) => a - b) { this.h = []; this.cmp = cmp; }
  size() { return this.h.length; }
  peek() { return this.h[0]; }
  push(v) {
    const h = this.h; h.push(v); let i = h.length - 1;
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (this.cmp(h[i], h[p]) >= 0) break;
      [h[i], h[p]] = [h[p], h[i]]; i = p;
    }
  }
  pop() {
    const h = this.h; if (!h.length) return undefined;
    const top = h[0], last = h.pop();
    if (h.length) {
      h[0] = last; let i = 0;
      for (;;) {
        const l = 2 * i + 1, r = l + 1; let s = i;
        if (l < h.length && this.cmp(h[l], h[s]) < 0) s = l;
        if (r < h.length && this.cmp(h[r], h[s]) < 0) s = r;
        if (s === i) break;
        [h[i], h[s]] = [h[s], h[i]]; i = s;
      }
    }
    return top;
  }
}

// Top K frequent: O(n log k)
function topKFrequent(nums, k) {
  const freq = new Map();
  for (const n of nums) freq.set(n, (freq.get(n) ?? 0) + 1);
  const heap = new MinHeap((a, b) => a[1] - b[1]);
  for (const entry of freq) { heap.push(entry); if (heap.size() > k) heap.pop(); }
  return heap.h.map(([n]) => n);
}

// Kth largest: size-k min-heap, top = answer
function kthLargest(nums, k) {
  const heap = new MinHeap();
  for (const n of nums) { heap.push(n); if (heap.size() > k) heap.pop(); }
  return heap.peek();
}

Trie: stores strings character by character in a tree; common prefixes are shared. Prefix search is O(length), independent of the dictionary size.

class TrieNode { constructor() { this.children = new Map(); this.end = false; } }

class Trie {
  constructor() { this.root = new TrieNode(); }
  insert(word) {
    let n = this.root;
    for (const c of word) {
      if (!n.children.has(c)) n.children.set(c, new TrieNode());
      n = n.children.get(c);
    }
    n.end = true;
  }
  #find(prefix) {
    let n = this.root;
    for (const c of prefix) { n = n.children.get(c); if (!n) return null; }
    return n;
  }
  search(word) { const n = this.#find(word); return !!n && n.end; }
  startsWith(prefix) { return this.#find(prefix) !== null; }

  suggest(prefix, limit = 5) {
    const start = this.#find(prefix); if (!start) return [];
    const out = [];
    (function dfs(n, path) {
      if (out.length >= limit) return;
      if (n.end) out.push(prefix + path);
      for (const [c, child] of [...n.children].sort()) dfs(child, path + c);
    })(start, "");
    return out;
  }
}
const t = new Trie(); ["shoe", "shoes", "shirt", "shop"].forEach(w => t.insert(w));
t.suggest("sho");    // ["shoe", "shoes", "shop"]

Complexity: insert/search O(L), space O(total chars). Real (ShopKart): search bar autocomplete, spell-check, IP routing (longest prefix match), word games. In production Elasticsearch/Redis sorted sets are used, but the concept is this. Variants: a word dictionary with wildcards ., top-K suggestions per node (frequency).

D22Dijkstra: Shortest Path (Weighted Graph)

Problem: in a weighted graph (non-negative weights) find the minimum distance from a source to every node (a delivery route, network latency). Idea: greedy: always take the node with the smallest distance so far (a min-heap) and relax its neighbors.

function dijkstra(graph, src) {
  const dist = new Map([...graph.keys()].map(n => [n, Infinity]));
  dist.set(src, 0);
  const pq = new MinHeap((a, b) => a[1] - b[1]);          // [node, distance]
  pq.push([src, 0]);

  while (pq.size()) {
    const [u, d] = pq.pop();
    if (d > dist.get(u)) continue;                         // stale entry skip
    for (const [v, w] of graph.get(u) ?? []) {
      const nd = d + w;
      if (nd < dist.get(v)) { dist.set(v, nd); pq.push([v, nd]); }   // relax
    }
  }
  return dist;
}

const g = new Map([
  ["Mumbai", [["Pune", 150], ["Surat", 280]]],
  ["Pune", [["Bangalore", 840]]],
  ["Surat", [["Bangalore", 1250]]],
  ["Bangalore", []],
]);
dijkstra(g, "Mumbai").get("Bangalore");    // 990

Complexity: O((V + E) log V). Limits: it does not work with negative weights (use Bellman-Ford). Variants: A (heuristic), BFS (unweighted), Floyd-Warshall (all pairs). To recover the path, keep a prev map. Real:* maps routing, delivery fee/route, network routing (OSPF), cheapest flights.

A1Consistent Hashing

Problem: with server = hash(key) % N, when a server is added/removed (N changes), almost every key’s mapping changes → a cache miss storm / data reshuffle.

Consistent hashing: place both servers and keys on a hash ring (0..2^32); a key goes to the next server clockwise. When a server is added/removed only a small portion (~1/N) of keys moves. Virtual nodes: each server has many points on the ring → an even distribution.

function hash(str) {                              // FNV-1a 32-bit
  let h = 2166136261;
  for (let i = 0; i < str.length; i++) { h ^= str.charCodeAt(i); h = Math.imul(h, 16777619); }
  return h >>> 0;
}

class ConsistentHash {
  constructor(nodes = [], vnodes = 100) {
    this.vnodes = vnodes; this.ring = [];             // sorted [{ h, node }]
    nodes.forEach(n => this.addNode(n));
  }
  addNode(node) {
    for (let i = 0; i < this.vnodes; i++) this.ring.push({ h: hash(`${node}#${i}`), node });
    this.ring.sort((a, b) => a.h - b.h);
  }
  removeNode(node) { this.ring = this.ring.filter(e => e.node !== node); }
  getNode(key) {
    if (!this.ring.length) return null;
    const h = hash(key);
    let lo = 0, hi = this.ring.length;
    while (lo < hi) { const m = (lo + hi) >> 1; this.ring[m].h < h ? (lo = m + 1) : (hi = m); }
    return this.ring[lo % this.ring.length].node;     // wrap-around
  }
}

const ch = new ConsistentHash(["cache-1", "cache-2", "cache-3"]);
ch.getNode("product:42");     // e.g. "cache-2"

Used in: Redis Cluster (hash slots, similar), DynamoDB, Cassandra, CDN/load balancers, memcached clients, sharded DB routing (Q55). Interview line: “With naive modulo all keys remap on a resize; with consistent hashing only K/N do.”

A2Bloom Filter

What: a probabilistic structure that answers “is this item in the set?” using very little memory. “Definitely not present” or “probably present.” False positives are possible, false negatives never; deletion is not supported (a counting bloom filter allows it).

How: a bit array (m bits) + k hash functions. Add: set the bits at the k positions. Check: if all k positions are 1 then “maybe present”, if any is 0 then “definitely not present.”

class BloomFilter {
  constructor(m = 1 << 20, k = 4) { this.m = m; this.k = k; this.bits = new Uint8Array((m >> 3) + 1); }
  #positions(item) {
    const h1 = hash(item), h2 = hash(item + "#salt") | 1;       // double hashing (hash(): A1)
    return Array.from({ length: this.k }, (_, i) => (h1 + i * h2) % this.m);
  }
  add(item) { for (const p of this.#positions(item)) this.bits[p >> 3] |= 1 << (p & 7); }
  mightContain(item) { return this.#positions(item).every(p => this.bits[p >> 3] & (1 << (p & 7))); }
}

const seen = new BloomFilter();
seen.add("user:42");
seen.mightContain("user:42");     // true
seen.mightContain("user:99");     // false (almost surely)

Sizing: m = -n ln(p) / (ln 2)^2, k = (m/n) ln 2 (n items, p false-positive rate). 1 crore items at 1% FP ~ 12 MB.

Real uses: cache penetration (Q58): before the DB check “does this key exist?”; a quick “is the username taken?” check; crawler visited URLs; Chrome safe browsing; avoiding disk reads in Cassandra/HBase/LSM-trees; a “content already seen” filter for recommendations; Redis BF.ADD (the RedisBloom module).

// Token bucket: capacity = max burst, refill = average rate
class TokenBucket {
  constructor(capacity, refillPerSec) {
    this.capacity = capacity; this.tokens = capacity; this.rate = refillPerSec; this.last = Date.now();
  }
  allow(cost = 1) {
    const now = Date.now();
    this.tokens = Math.min(this.capacity, this.tokens + ((now - this.last) / 1000) * this.rate);   // lazy refill
    this.last = now;
    if (this.tokens >= cost) { this.tokens -= cost; return true; }
    return false;
  }
}

// Sliding window log (per key)
class SlidingWindowLog {
  constructor(limit, windowMs) { this.limit = limit; this.windowMs = windowMs; this.hits = new Map(); }
  allow(key) {
    const now = Date.now();
    const recent = (this.hits.get(key) ?? []).filter(t => t > now - this.windowMs);
    if (recent.length >= this.limit) { this.hits.set(key, recent); return false; }
    recent.push(now); this.hits.set(key, recent); return true;
  }
}

// Sliding window counter: estimate = prev * (1 - elapsedFraction) + current
function slidingCounter(prevCount, currCount, elapsedMs, windowMs) {
  return prevCount * (1 - elapsedMs / windowMs) + currCount;     // < limit to allow
}

class LeastConnections {
  constructor(servers) { this.conns = new Map(servers.map(s => [s, 0])); }
  acquire() {
    let best = null;
    for (const [s, c] of this.conns) if (best === null || c < this.conns.get(best)) best = s;
    this.conns.set(best, this.conns.get(best) + 1);
    return best;
  }
  release(s) { this.conns.set(s, this.conns.get(s) - 1); }
}

// Weighted (smooth WRR, nginx style)
class WeightedRR {
  constructor(servers) { this.s = servers.map(x => ({ ...x, current: 0 })); }   // [{name, weight}]
  next() {
    const total = this.s.reduce((t, x) => t + x.weight, 0);
    for (const x of this.s) x.current += x.weight;
    const best = this.s.reduce((a, b) => (b.current > a.current ? b : a));
    best.current -= total;
    return best.name;
  }
}

const ALPHABET = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";
function toBase62(num) {
  let n = BigInt(num), out = "";
  if (n === 0n) return "0";
  while (n > 0n) { out = ALPHABET[Number(n % 62n)] + out; n /= 62n; }
  return out;
}

// Snowflake: 64-bit = [41 bits time][10 bits machine][12 bits sequence] -> 4096 ids/ms/machine
class Snowflake {
  constructor(machineId, epoch = 1700000000000n) {
    this.machine = BigInt(machineId) & 1023n; this.epoch = epoch; this.seq = 0n; this.last = -1n;
  }
  next() {
    let now = BigInt(Date.now());
    if (now < this.last) throw new Error("Clock moved backwards");         // NTP issue
    if (now === this.last) {
      this.seq = (this.seq + 1n) & 4095n;
      if (this.seq === 0n) while ((now = BigInt(Date.now())) <= this.last);
    } else this.seq = 0n;
    this.last = now;
    return ((now - this.epoch) << 22n) | (this.machine << 12n) | this.seq;
  }
}
const gen = new Snowflake(7);  gen.next();       // time-sortable unique id

Trade-offs: for a URL shortener a counter + base62 (predictable, enumerable → salt/shuffle or random for security). Public IDs: UUID/ULID (not guessable), internal: bigint. Postgres: random UUID v4 inserts fragment the B-tree; UUIDv7 is better. Clock skew is the risk of distributed time-based IDs.

A6Cache Eviction: LRU (O(1)) and LFU

Eviction policies: what to remove when the cache is full?

Policy Removes Best
LRU (Least Recently Used) The one not used for the longest time General purpose (the most common)
LFU (Least Frequently Used) The one used the fewest times Stable popularity (hot items)
FIFO The first one that came in Simple
TTL Expired entries Time-bound data
Random Any Redis allkeys-random

LRU in O(1): a Hash Map + a Doubly Linked List (the front of the list = most recent, the back = LRU).

class Node { constructor(k, v) { this.k = k; this.v = v; this.prev = this.next = null; } }

class LRUCache {
  constructor(capacity) {
    this.cap = capacity; this.map = new Map();
    this.head = new Node(); this.tail = new Node();            // sentinels
    this.head.next = this.tail; this.tail.prev = this.head;
  }
  #remove(n) { n.prev.next = n.next; n.next.prev = n.prev; }
  #addFront(n) { n.next = this.head.next; n.prev = this.head; this.head.next.prev = n; this.head.next = n; }

  get(key) {
    const n = this.map.get(key);
    if (!n) return -1;
    this.#remove(n); this.#addFront(n);                        // recently used bana do
    return n.v;
  }
  put(key, val) {
    let n = this.map.get(key);
    if (n) { n.v = val; this.#remove(n); this.#addFront(n); return; }
    if (this.map.size === this.cap) {
      const lru = this.tail.prev; this.#remove(lru); this.map.delete(lru.k);
    }
    n = new Node(key, val); this.map.set(key, n); this.#addFront(n);
  }
}
const c = new LRUCache(2); c.put(1, "a"); c.put(2, "b"); c.get(1); c.put(3, "c");   // key 2 evict

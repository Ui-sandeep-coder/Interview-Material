Scope, Hoisting and Variables 6 questions

1Scope in JS (Global, Functional, Block)

What: scope is the place up to which a variable is visible and usable. JS has 3 main scopes (plus module scope when you use ES modules).

Scope How it is created Which variables
Global At the top level of the file/window var, let, const, functions
Function Inside every function var, let, const (not visible outside the function)
Block { } (if, for, while, a plain block) Only let, const, class

Why: keeping variables within their own limit prevents naming conflicts and accidental changes.

var globalVar = "sab jagah";

function checkout() {
  var fnVar = "only inside checkout";
  if (true) {
    var a = 1;
    let b = 2;
    const c = 3;
  }
  console.log(a);     // 1
  console.log(b);     // ReferenceError
}

Real bug (ShopKart): a var discount written inside a for (var i...) loop was visible outside the loop too, and the total came out wrong. The fix was let/const.

Interview line: “In modern JS we avoid var because it is not block-scoped.”

2Scope Chaining

What: when JS needs a variable it first looks in the current scope; if not found, in the outer (parent) scope, then its outer one… all the way to global. This is the scope chain. If it is not even in global, you get a ReferenceError.

const tax = 0.18;                    // global

function cart() {
  const shipping = 50;               // cart scope
  function total(price) {
    const discount = 100;            // total scope
    return price + price * tax + shipping - discount;
  }
  return total(1000);
}

Important: the chain is lexical (from where the function was written), not from where it is called (see Q57). Closures are built on this chain. In variable shadowing (Q41), the first variable found in the chain wins.

5Temporal Dead Zone (TDZ)

What: the binding of let, const, class is created (hoisted) as soon as the scope starts, but it is not initialized until the declaration line. The time from the start of the scope to the declaration line is the Temporal Dead Zone. Accessing it during this time throws a ReferenceError.

{
  console.log(b);       // ReferenceError: Cannot access 'b' before initialization
  let b = 5;
  console.log(b);       // 5
}

Why it exists: the silent undefined of var hid bugs. The TDZ catches the mistake immediately.

Proof that hoisting happens:

let x = "outer";
{
  console.log(x);
  let x = "inner";
}

Tricky: default params also have a TDZ: function f(a = b, b = 1) {} → f() errors. typeof also errors in the TDZ (Q55).

Prototypes 3 questions

7Prototypes in JS

What: every object in JS has a hidden link [[Prototype]] that points to another object. If a property is not found, JS looks there. This is how inheritance works (prototype-based, not class-based).

Why: instead of copying methods into every object, you keep them once on the prototype, which saves memory.

const animal = { eats: true, walk() { return "walking"; } };
const dog = Object.create(animal);    // dog.[[Prototype]] = animal
dog.barks = true;

console.log(dog.eats);
console.log(dog.walk());              // "walking"
console.log(Object.getPrototypeOf(dog) === animal);   // true
console.log(dog.hasOwnProperty("eats")); // false

Access: Object.getPrototypeOf(obj) (the right way), obj.__proto__ (the old accessor, avoid in production code). class is also prototypes underneath; it is just syntax sugar.

8The Prototype Object (.prototype vs __proto__)

The most common confusion:

  • Fn.prototype: only functions (constructors) have it. It is the object that becomes the [[Prototype]] of instances created by that constructor.
  • obj.__proto__: every object has it; it is its actual prototype.
function Product(name) { this.name = name; }
Product.prototype.getInfo = function () { return "Product: " + this.name; };

const p = new Product("Shoes");

p.__proto__ === Product.prototype;                  // true
Product.prototype.constructor === Product;          // true
p.getInfo();
Object.getPrototypeOf(Product) === Function.prototype; // true

Memory benefit: if 1000 products are created, getInfo exists once in memory (on the prototype), not copied into each instance.

In an ES6 class:

class Product {
  constructor(name) { this.name = name; }
  getInfo() { return this.name; }
}
9Prototype Chaining

What: a prototype has its own prototype, and so on… this chain ends at null. Property lookup walks up the chain.

function Animal() {}
Animal.prototype.eat = () => "eating";
function Dog() {}
Dog.prototype = Object.create(Animal.prototype);   // chain jodi
Dog.prototype.constructor = Dog;
Dog.prototype.bark = () => "woof";

const d = new Dog();
d.bark();   // Dog.prototype
d.eat();    // Animal.prototype
d.toString(); // Object.prototype
// Chain: d -> Dog.prototype -> Animal.prototype -> Object.prototype -> null

Lookup rule: first its own properties, then up the chain. If not found, undefined. On write, the property is always created on the object itself (not on the prototype), which causes shadowing.

Performance: the chain should not be very long. instanceof checks this same chain. for...in also returns enumerable properties from the chain; Object.keys returns only own ones.

Real use: array methods (map, filter) live on Array.prototype; through this chain you can call .toString() on an array.

Functions, Closures and Object Basics 8 questions

10Closures

What: when an inner function remembers the variables of its outer function, even after the outer function has finished. Function + its lexical environment = closure.

Why: private data, preserving state, function factories, and patterns like debounce/memoize/once.

function createCart() {
  let items = [];
  return {
    add: item => { items.push(item); return items.length; },
    count: () => items.length,
  };
}
const cart = createCart();
cart.add("shoes");
cart.count();     // 1
cart.items;       // undefined (private)

Common uses: data hiding, once(fn), debounce, counters, event handlers, React hooks (useState remembers state through a closure).

Classic bug:

for (var i = 1; i <= 3; i++) setTimeout(() => console.log(i), 100);  // 4 4 4
for (var i = 1; i <= 3; i++) ((j) => setTimeout(() => console.log(j), 100))(i);

Downsides: too many closures, or big objects held in references, cause a memory leak (Q77). In React, the stale closure bug.

11Pass by Reference vs Pass by Value

Truth: JS is always pass by value. The difference is that for objects the value is a copy of the reference (address). This is also called “call by sharing”.

function changePrimitive(n) { n = 100; }
let x = 10; changePrimitive(x); console.log(x);   // 10 (copy badli)

function mutate(obj)  { obj.price = 999; }
function reassign(obj){ obj = { price: 1 }; }

const product = { price: 500 };
mutate(product);   console.log(product.price);      // 999
reassign(product); console.log(product.price);      // 999 (original safe)

Takeaway: if you change properties of an object inside a function it shows outside; if you assign a new object to the parameter it does not.

Real bug: applyCoupon(cart) mutated the cart object and the UI did not update (React saw the same reference). Fix: return a new object, { ...cart, total: ... }. For copying, see shallow vs deep (P10).

12Currying in JS

What: converting a function that takes multiple arguments into a chain of functions that take one argument each: f(a, b, c) → f(a)(b)(c).

Why: partial application (fix some arguments first to make a reusable function), function composition, config first and data later.

const add = a => b => c => a + b + c;
add(1)(2)(3);          // 6

const applyDiscount = percent => price => price - (price * percent) / 100;
const festival = applyDiscount(20);
festival(1000);        // 800
festival(500);         // 400

function curry(fn) {
  return function curried(...args) {
    if (args.length >= fn.length) return fn.apply(this, args);
    return (...next) => curried.apply(this, [...args, ...next]);
  };
}
const sum3 = curry((a, b, c) => a + b + c);
sum3(1)(2)(3);  sum3(1, 2)(3);  sum3(1)(2, 3);   // sab 6

Currying vs Partial application: currying is always a chain of 1 argument each. Partial = fix a few arguments and get a new function for the rest (bind does this). Limitation: fn.length does not count default/rest params.

13The Infinite Currying Problem

Question: sum(1)(2)(3)...() or sum(1)(2)(3): however many times you call it, you must get the result. The number of arguments is unknown.

Version 1: stops with an empty call () (the most common):

function sum(a) {
  return function (b) {
    if (b === undefined) return a;
    return sum(a + b);
  };
}
sum(1)(2)(3)();     // 6

Version 2: multiple args also allowed, sum(1,2)(3)(4,5)():

function sum(...a) {
  const total = a.reduce((x, y) => x + y, 0);
  return (...b) => (b.length ? sum(total, ...b) : total);
}
sum(1, 2)(3)(4, 5)();    // 15

Version 3: without (), using the valueOf/toString trick:

function sum(a) {
  const f = b => sum(a + b);
  f.valueOf = () => a;
  f.toString = () => String(a);
  return f;
}
sum(1)(2)(3) + 0;

Why they ask this: it tests closures + recursion + type coercion (Q30) together.

14Memoization in JS

What: caching a function’s result so the calculation is not repeated for the same input. It uses a closure + Map.

Why: to speed up expensive/pure functions (fibonacci, price calculation, filtering).

function memoize(fn) {
  const cache = new Map();
  return function (...args) {
    const key = JSON.stringify(args);
    if (cache.has(key)) return cache.get(key);   // hit
    const result = fn.apply(this, args);
    cache.set(key, result);
    return result;
  };
}

const slowSquare = n => { for (let i = 0; i < 1e8; i++); return n * n; };
const fast = memoize(slowSquare);
fast(9);
fast(9);   // instant (cache hit)

const fib = memoize(n => (n < 2 ? n : fib(n - 1) + fib(n - 2)));

Note: only for pure functions (same input → same output). JSON.stringify keys can be wrong with objects/functions. The cache grows unbounded, so use LRU/TTL (P12). In React, useMemo and React.memo rest on the same idea.

15Rest Parameter

What: the ...name syntax that collects the remaining arguments of a function into a real array. It can only be the last parameter.

function addToCart(user, ...items) {
  console.log(user);    // "Riya"
  console.log(items);   // ["shoes", "bag", "watch"] (real array)
}
addToCart("Riya", "shoes", "bag", "watch");

const total = (...nums) => nums.reduce((a, b) => a + b, 0);
total(1, 2, 3, 4);   // 10

const [first, ...others] = [1, 2, 3];
const { id, ...rest } = { id: 1, a: 2, b: 3 }; // rest = { a: 2, b: 3 }

Difference from arguments: arguments is array-like (no map/filter) and does not exist in arrow functions. Rest is a real array and works in every function type. So prefer rest.

16Spread Operator

What: ... that expands an iterable/object into elements. (Rest = collect, Spread = expand.)

// Array
const a = [1, 2], b = [3, 4];

const copy = [...a];                          // shallow copy

// Function call

const defaults = { theme: "light", lang: "en" };
const settings = { ...defaults, theme: "dark" };   // { theme:"dark", lang:"en" }

// React immutable update
setCart(prev => ({ ...prev, items: [...prev.items, newItem] }));

[..."hello"];                                  // ["h","e","l","l","o"]

Important: it is a shallow copy: nested objects are still shared. Object spread copies only own enumerable properties. Spreading null/undefined is safe in objects but an error in arrays.

Generators, Async and the Event Loop 7 questions

18Generator Functions in JS

What: a special function created with function* that can pause (yield) and resume in the middle. Calling it does not run the code; it returns a generator object (iterator), and .next() runs it step by step.

function* idGenerator() {
  let id = 1;
  while (true) yield id++;
}
const gen = idGenerator();
gen.next();   // { value: 1, done: false }
gen.next();   // { value: 2, done: false }

function* demo() {
  const name = yield "tell your name";
  console.log("Hello", name);
  return "end";
}
const g = demo();
g.next();
g.next("Riya");    // logs "Hello Riya" -> { value: "end", done: true }

Methods: next(v), return(v) (finish early), throw(err) (throw an error inside). yield* delegates to another generator/iterable.

Why / Real use:

  • Lazy sequences: paginated products one at a time.
  • Custom iterables: writing [Symbol.iterator] as a generator is easy.
  • Async flow control: the co library before async/await; redux-saga is still based on generators.
  • Async generators (async function* + for await) for streams/pagination.
async function* fetchPages(url) {
  let page = 1;
  while (true) {
    const res = await fetch(`${url}?page=${page++}`).then(r => r.json());
    if (!res.items.length) return;
    yield res.items;
  }
}
for await (const items of fetchPages("/api/products")) render(items);
19How is JavaScript single-threaded?

What: the JS engine has only one Call Stack, so only one task executes at a time. One thread = one main execution flow.

Then how does async work? The browser/Node does work outside the JS engine (Web APIs: timers, network, DOM events; these are other threads/C++). When the work completes, the callback comes into a queue and the event loop puts it on the call stack when it is empty (Q21).

console.log("A");
setTimeout(() => console.log("B"), 0);
console.log("C");
// A C B

Benefit: no race conditions/locks, a simple mental model. Drawback: a heavy synchronous loop freezes the entire UI:

while (Date.now() - start < 5000) {}

Solution: split heavy work into chunks, send it to Web Workers (Q78), or do it on the backend. Note: “single-threaded” is about JS execution, not the whole browser.

20Callbacks: why do we need them?

What: a callback is a function passed as an argument to another function and called later (when the work is done).

Why: JS is single-threaded; if waiting for network/file/timer blocked, the app would freeze. A callback says: “when the work is done, run this function.”

// Synchronous callback
[1, 2, 3].map(n => n * 2);

// Asynchronous callback
setTimeout(() => console.log("after 2 sec"), 2000);

// Error-first callback (Node style)
fs.readFile("data.json", (err, data) => {
  if (err) return console.error(err);
  console.log(data);
});

// Custom
function getProduct(id, callback) {
  setTimeout(() => callback({ id, name: "Shoes" }), 500);
}
getProduct(1, product => console.log(product.name));

Problems: callback hell (Q45), scattered error handling, “inversion of control” (you trust someone else’s code to call your callback exactly once). That is why Promises/async-await arrived.

21Event Loop

What: the mechanism that continuously checks: “Is the Call Stack empty? Then take the next task from the queue and put it on the stack.” This is how async works on a single thread.

Players: Call Stack, Web APIs, Microtask queue, Task (callback/macrotask) queue, Event loop.

Order in every cycle:

  1. Run all synchronous code on the call stack.
  2. Stack empty → run all microtasks (including new ones) until the queue is empty.
  3. (Browser) render/paint if needed.
  4. Take one macrotask (setTimeout, DOM event, I/O) and run it.
  5. Repeat from step 2.
console.log("1 sync");
setTimeout(() => console.log("5 macrotask"), 0);
Promise.resolve().then(() => console.log("3 microtask"));
queueMicrotask(() => console.log("4 microtask"));
console.log("2 sync");
// 1 sync, 2 sync, 3 microtask, 4 microtask, 5 macrotask

Real case: in ShopKart, a heavy price calculation sat in a sync loop after “Add to cart”, so the button animation stuttered. Moving the calculation to setTimeout/a worker made the UI smooth. Takeaway: setTimeout(fn, 0) does not mean “immediately”, it means “after the current stack + microtasks”.

22Callback Queue (Task / Macrotask Queue)

What: the queue where completed callbacks of Web APIs wait: setTimeout, setInterval, DOM events (click), XMLHttpRequest, MessageChannel, I/O. The event loop takes them one by one, when the call stack is empty (and after microtasks).

Flow:

setTimeout(() => console.log("timeout"), 0);
button.addEventListener("click", () => console.log("click"));
  1. setTimeout is handed to the Web API and the timer runs.
  2. The timer finishes → the callback goes into the callback queue.
  3. Event loop: stack empty + microtasks empty → the callback goes onto the stack.

Notes:

  • The queue is FIFO; but the minimum delay of setTimeout(fn, 0) can be ~1-4 ms in browsers (a 4 ms clamp for nested timers).
  • setTimeout’s delay is a minimum, not a guarantee (it runs late if the stack is busy).
  • The microtask queue has a higher priority than this one (Q23).
23Microtask Queue

What: the higher-priority queue that holds: Promise callbacks (.then/.catch/.finally), the code after await, queueMicrotask, MutationObserver. In Node process.nextTick is separate and runs even earlier (Q81).

Rule: when the call stack becomes empty, the event loop drains the entire microtask queue (including new microtasks added in between) and only then goes to the next macrotask or rendering.

setTimeout(() => console.log("macro"), 0);
Promise.resolve().then(() => console.log("micro 1"))
       .then(() => console.log("micro 2"));
console.log("sync");
// sync, micro 1, micro 2, macro

With async/await:

async function f() {
  console.log("A");
  await null;
  console.log("B");
}
f(); console.log("C");        // A C B

Danger: if microtasks keep scheduling new microtasks, macrotasks/render starve (Q34).

24Promises

What: an object that represents a value (or error) that will arrive in the future. 3 states: pending → fulfilled / rejected (once settled it never changes).

const getStock = id => new Promise((resolve, reject) => {
  setTimeout(() => (id > 0 ? resolve({ id, stock: 12 }) : reject(new Error("Invalid id"))), 300);
});

getStock(1)
  .then(res => res.stock)
  .then(stock => console.log(stock))
  .catch(err => console.error(err))
  .finally(() => console.log("loader band"));

Key points:

  • .then() always returns a new promise (hence chaining).
  • If you return a promise inside .then, the chain waits for it; if you throw, it goes to the next .catch.
  • A promise’s executor runs synchronously; .then callbacks run async (microtask).
  • An unhandled rejection is a bug (the unhandledrejection event).

Combinators: Promise.all (all succeed), allSettled (every result), race (first to settle), any (first success). Implementations are in P3.

Why promises: no more callback hell, error handling in one place, and they are the base of async/await.

Events 5 questions

25Event Propagation

What: when an event happens in the DOM (a click), it does not stay limited to the target element; it travels in three phases:

  1. Capturing phase: window → document → … → up to the target’s parent (top to bottom).
  2. Target phase: on the actual element.
  3. Bubbling phase: from the target back up to window.
<div id="card"><button id="buy">Buy</button></div>

card.addEventListener("click", () => console.log("card bubble"));
card.addEventListener("click", () => console.log("card capture"), true);
buy.addEventListener("click", () => console.log("button"));
// Click on button: card capture -> button -> card bubble

Useful properties: e.target (the element actually clicked), e.currentTarget (the element the listener is attached to), e.eventPhase. This same propagation makes event delegation (Q29) possible.

26Event Bubbling

What: after running on the target, the event goes up to the parent → grandparent → … → document, and listeners of the same type run at each place. This is the default behaviour (unless capture: true).

document.querySelector(".product-card").addEventListener("click", () => openDetails());
document.querySelector(".add-btn").addEventListener("click", () => addToCart());

Real problem: in ShopKart, pressing “Add to cart” inside a card also opened the product page. Fix: e.stopPropagation() or checking e.target.closest(".add-btn") in delegation.

Note: not all events bubble: focus, blur, mouseenter, mouseleave, load, scroll (on an element) do not bubble. Their bubbling versions: focusin, focusout, mouseover/out.

27Event Capturing (Trickling)

What: the first phase of an event, where it travels from the root down to the target. Default listeners do not run in capturing; to enable it use addEventListener(type, fn, true) or { capture: true }.

parent.addEventListener("click", () => console.log("parent capture"), { capture: true });
child.addEventListener("click", () => console.log("child"));
parent.addEventListener("click", () => console.log("parent bubble"));
// child click: parent capture -> child -> parent bubble

When to use:

  • To catch/stop an event before it reaches the child (analytics, global click blockers, clicks outside a modal).
  • To listen on a parent for non-bubbling events (focus): parent.addEventListener("focus", fn, true).
  • If you call stopPropagation during capturing, the child will never receive the event.

Options: { once: true }, { passive: true } (scroll performance), { signal } (remove many listeners at once with an AbortController).

29Event Delegation

What: instead of attaching a listener to every child, attach one listener on a common parent, and use bubbling and e.target to decide which child was clicked.

Why: fewer listeners (memory/performance), and it works on dynamically added elements without new listeners.

// Delegation: ek listener
document.querySelector("#product-list").addEventListener("click", e => {
  const card = e.target.closest(".product-card");
  if (!card || !list.contains(card)) return;

31Throttle

What: letting a function run at most once per fixed interval, no matter how many times the event fires.

Why: events like scroll, resize, mousemove fire 100+ times per second; running a heavy handler every time makes the UI stutter.

function throttle(fn, limit) {
  let lastCall = 0;
  return function (...args) {
    const now = Date.now();
    if (now - lastCall >= limit) {
      lastCall = now;
      return fn.apply(this, args);
    }
  };
}

33How does JavaScript parse and compile your code? (Step by step)

(The example is the V8 engine: Chrome/Node. The details change over time; the concept is the same.)

  1. Download/Load: the source code reaches the engine.
  2. Scanner / Tokenizer (lexical analysis): splits code into tokens: const, x, =, 5.
  3. Parser (syntax analysis): builds an AST (Abstract Syntax Tree) from tokens. Syntax errors are caught here (SyntaxError). Lazy parsing: inner functions are only pre-parsed first and fully parsed when called (fast startup).
  4. Interpreter (Ignition): generates bytecode from the AST and starts running it immediately (fast startup).
  5. Profiling: the engine watches which code is hot (runs repeatedly).
  6. Optimizing JIT compiler (TurboFan): compiles hot code into optimized machine code, with type assumptions (e.g. “this is always a number”).
  7. Deoptimization: if an assumption breaks (a string suddenly arrives), the optimized code is thrown away and it goes back to bytecode.
  8. Execution Context + Call Stack: the global context is created (creation phase: hoisting, this; execution phase: line by line, Q49).
  9. Memory management: heap allocation + Garbage Collection (Q51).
Source -> Tokens -> AST -> Bytecode (Ignition) -> Hot? -> Machine code (TurboFan)
                                                      ^-- deopt if the type changes

Practical takeaway: always pass arguments of the same type and keep object shapes consistent (same keys, same order), and JIT optimization works well. JS is both “interpreted” and “compiled” (JIT).

34If a microtask keeps adding a new microtask forever (infinite), how do you handle it?

Problem: the event loop does not move on until the microtask queue is completely empty. If every microtask queues a new one, the queue is never empty → macrotasks (timers, clicks) and rendering never run → the page freezes (microtask starvation). It is more dangerous than an infinite loop because the stack looks empty but the UI still hangs.

setTimeout(() => console.log("will never run"), 0);

Solutions:

  1. Have a termination condition (fix the design first).
  2. Yield to a macrotask in between (let the event loop breathe):
async function processAll(items) {
  for (let i = 0; i < items.length; i++) {
    handle(items[i]);
    if (i % 100 === 0) await new Promise(r => setTimeout(r));
  }
}
  1. Chunking: do work in small batches with setTimeout, requestAnimationFrame, requestIdleCallback, MessageChannel or scheduler.yield() (where available).
  2. Put heavy work in a Web Worker (Q78).
  3. Debug: a long task shows in the DevTools Performance tab; turn recursion into a loop/batches.

Interview point: this is different from setTimeout recursion (each step is a macrotask, so the UI stays alive). Only microtask recursion starves.

38mapLimit

What: running an async function on each item of an array, but with at most limit tasks in parallel, and returning results in order. map + concurrency control.

Why: if you fire 500 image uploads / 1000 API calls at once, the server returns 429 Too Many Requests, or the browser hits its connection limit (6/host) and memory suffers. Sequential is too slow. The middle path: a limit.

Callback style (like the async library, the classic interview version):

function mapLimit(arr, limit, iteratee, done) {
  const results = new Array(arr.length);
  let started = 0, finished = 0, failed = false;
  if (!arr.length) return done(null, results);

  function next() {
    if (failed || started >= arr.length) return;
    const i = started++;
    iteratee(arr[i], (err, val) => {
      if (failed) return;
      if (err) { failed = true; return done(err); }
      results[i] = val;
      if (++finished === arr.length) return done(null, results);
      next();
    });
  }
  for (let k = 0; k < Math.min(limit, arr.length); k++) next();
}

// Use

55Temporal Dead Zone: why does typeof x throw for let x but not for an undeclared variable?

First, the behaviour:

let x = 5;

Reason (at spec level):

  1. Undeclared variable: there is no binding in the scope chain at all. For such an “unresolvable reference” the spec makes typeof a special case: instead of an error it returns the string "undefined". This was designed to keep old feature detection (typeof Promise !== "undefined") safe.
  2. let/const/class in the TDZ: the binding exists (it was hoisted when the scope started) but it is uninitialized. The reference resolves, so the special case does not apply; now the value must be read, and reading an uninitialized binding throws a ReferenceError.

Meaning: typeof’s safety applies only when there is no binding, not when a binding exists but is not initialized. The TDZ error is also proof that let is hoisted (otherwise you would get "undefined").

  console.log(typeof y);
  let y;
}
console.log(typeof y);

Practical: typeof is no longer “completely safe”. For feature detection typeof window !== "undefined" still works (there is no TDZ in the global scope whether window exists or not). var has no TDZ; typeof v gives "undefined".

57Lexical Scope vs Dynamic Scope. Which does JS use?

Lexical (static) scope: which variable you get is decided by where the function is written (source structure). Dynamic scope: it is decided by where the function is called from (the call stack).

JavaScript uses lexical scope.

const name = "global";

function show() { console.log(name); }

function run() {
  const name = "run";
  show();
}
run();                                      // "global"

How dynamic scope would behave (Bash, old Lisp, Perl local): the show() above would look at run’s call stack and print "run".

But this behaves like dynamic scoping: this depends on how the call is made (Q46). That is why arrow functions made this lexical too.

const o = { n: "obj", f() { return this.n; } };
const g = o.f;
o.f();   // "obj"
g();

Why lexical is better: you can tell where a variable will come from just by reading the code (static analysis, minifiers, closures). Closure is a direct result of lexical scope.

Why NaN !== NaN: JS numbers follow the IEEE 754 standard, where NaN means “not a number”, i.e. “this is not any valid number, and two different invalid computations cannot be considered equal” (0/0 and Math.sqrt(-1) are not the same). The standard says NaN is unordered/unequal to everything (even itself). === follows this rule.

Why Object.is(NaN, NaN) is true: Object.is uses SameValue, which checks “identity” (is this exactly the same value?), not numerical comparison. So NaN equals NaN, and +0 and -0 are different (1/+0 = Infinity, 1/-0 = -Infinity, so they behave differently).

Ways to check NaN: Number.isNaN(x) (best), Object.is(x, NaN), x !== x. The global isNaN("abc") coerces (true), so use Number.isNaN. React useEffect dependencies and the useState bail-out use Object.is.

59Prototype Pollution. How can unsafe object merge become a security issue?

What: an attacker uses __proto__ (or constructor.prototype) to inject properties into Object.prototype. Because all objects inherit from Object.prototype, that property appears on all objects in the app.

Vulnerable merge function:

function merge(target, source) {
  for (const key in source) {
    if (typeof source[key] === "object" && source[key] !== null) {
      target[key] = merge(target[key] || {}, source[key]);
    } else {
      target[key] = source[key];
    }
  }
  return target;
}

const payload = JSON.parse('{ "__proto__": { "isAdmin": true } }');

const user = {};
console.log(user.isAdmin);

Impact (ShopKart example): the settings/profile update API deep-merges the user’s JSON into config. The attacker sends __proto__.isAdmin = true; later every user passes the if (user.isAdmin) check. Result: privilege escalation, XSS (template gadgets), denial of service, and sometimes RCE (in Node). Real libraries (lodash merge, defaultsDeep, jQuery extend) have had CVEs.

Prevention:

  1. Block dangerous keys: __proto__, constructor, prototype.

  for (const key of Object.keys(source)) {
    if (BLOCKED.has(key)) continue;
    const v = source[key];
    target[key] = v && typeof v === "object" && !Array.isArray(v) ? safeMerge(target[key] ?? {}, v) : v;
  }
  return target;
}
  1. Prototype-less objects: Object.create(null) or Map for dictionaries.
  2. Own-property checks: read with Object.hasOwn(obj, key) (not in / obj.key).
  3. Object.freeze(Object.prototype) (test the side effects) or the Node flag --disable-proto=delete.
  4. Schema validation (Zod/Ajv, additionalProperties: false) on input.
  5. Keep libraries updated, npm audit.

class MyPromise {
  #state = "pending";
  #value;
  #handlers = [];

  constructor(executor) {
    let called = false;
    const resolve = v => { if (called) return; called = true; this.#resolveWith(v); };
    const reject = e => { if (called) return; called = true; this.#settle("rejected", e); };
    try { executor(resolve, reject); } catch (e) { reject(e); }
  }

  #resolveWith(v) {
    if (v === this) return this.#settle("rejected", new TypeError("Chaining cycle"));
    if (v && (typeof v === "object" || typeof v === "function")) {
      let then;
      try { then = v.then; } catch (e) { return this.#settle("rejected", e); }
      if (typeof then === "function") {
        let done = false;
        try {
          then.call(v,
            y => { if (!done) { done = true; this.#resolveWith(y); } },
            r => { if (!done) { done = true; this.#settle("rejected", r); } });
        } catch (e) { if (!done) { done = true; this.#settle("rejected", e); } }
        return;
      }
    }
    this.#settle("fulfilled", v);
  }

  #settle(state, value) {
    if (this.#state !== "pending") return;
    this.#state = state; this.#value = value;
    this.#flush();
  }

  #flush() {
    if (this.#state === "pending") return;
    const hs = this.#handlers; this.#handlers = [];
    hs.forEach(h => queueMicrotask(h));
  }

  then(onFulfilled, onRejected) {
    return new MyPromise((resolve, reject) => {
      this.#handlers.push(() => {
        const cb = this.#state === "fulfilled" ? onFulfilled : onRejected;
        if (typeof cb !== "function") {              // pass-through
          return this.#state === "fulfilled" ? resolve(this.#value) : reject(this.#value);
        }
        try { resolve(cb(this.#value)); } catch (e) { reject(e); }
      });
      this.#flush();
    });
  }

  catch(onRejected) { return this.then(undefined, onRejected); }

  finally(cb) {
    return this.then(
      v => MyPromise.resolve(cb()).then(() => v),
      e => MyPromise.resolve(cb()).then(() => { throw e; })
    );
  }

  static resolve(v) { return v instanceof MyPromise ? v : new MyPromise(res => res(v)); }
  static reject(e) { return new MyPromise((_, rej) => rej(e)); }
}

P5Debounce polyfill (leading, trailing, cancel, flush)
function debounce(fn, wait = 0, { leading = false, trailing = true } = {}) {
  let timer = null, lastArgs, lastThis, result;

  function invoke() {
    const args = lastArgs, ctx = lastThis;
    lastArgs = lastThis = undefined;
    result = fn.apply(ctx, args);
    return result;
  }

  function debounced(...args) {
    lastArgs = args; lastThis = this;
    const callNow = leading && !timer;
    clearTimeout(timer);
    timer = setTimeout(() => {
      timer = null;
      if (trailing && lastArgs) invoke();
    }, wait);
    if (callNow) invoke();
    return result;
  }

  debounced.cancel = () => { clearTimeout(timer); timer = null; lastArgs = lastThis = undefined; };
  debounced.flush = () => {
    if (timer) { clearTimeout(timer); timer = null; if (lastArgs) return invoke(); }
    return result;
  };
  return debounced;
}

P6Throttle polyfill (leading, trailing, cancel)
function throttle(fn, wait, { leading = true, trailing = true } = {}) {
  let timer = null, lastArgs, lastThis, lastCall = 0;

  function run(time) {
    lastCall = time;
    const args = lastArgs, ctx = lastThis;
    lastArgs = lastThis = undefined;
    fn.apply(ctx, args);
  }

  function throttled(...args) {
    const now = Date.now();
    if (!lastCall && !leading) lastCall = now;
    const remaining = wait - (now - lastCall);
    lastArgs = args; lastThis = this;

    if (remaining <= 0 || remaining > wait) {
      if (timer) { clearTimeout(timer); timer = null; }
      run(now);
    } else if (!timer && trailing) {
      timer = setTimeout(() => {
        timer = null;
        if (lastArgs) run(leading ? Date.now() : 0);
      }, remaining);
    }
  }

  throttled.cancel = () => { clearTimeout(timer); timer = null; lastArgs = lastThis = undefined; lastCall = 0; };
  return throttled;
}

Difference from debounce: throttle runs regularly every wait; the trailing option ensures the user’s last event is not missed (scrolling stopped, run once at the last position).

P7Event Emitter

What: the Pub/Sub pattern: on (subscribe), off (unsubscribe), once, emit (publish). Node’s EventEmitter, the browser’s EventTarget, and the event buses of Redux/Vue are built on this idea.

class EventEmitter {
  #events = new Map();

  on(name, listener) {
    if (!this.#events.has(name)) this.#events.set(name, []);
    this.#events.get(name).push(listener);
    return () => this.off(name, listener);           // unsubscribe function
  }

  off(name, listener) {
    const list = this.#events.get(name);
    if (!list) return this;
    const filtered = list.filter(l => l !== listener && l.original !== listener);
    filtered.length ? this.#events.set(name, filtered) : this.#events.delete(name);
    return this;
  }

  once(name, listener) {
    const wrapper = (...args) => { this.off(name, wrapper); listener(...args); };
    wrapper.original = listener;
    return this.on(name, wrapper);
  }

  emit(name, ...args) {
    const list = this.#events.get(name);
    if (!list) return false;
    [...list].forEach(l => l(...args));
    return true;
  }

  listenerCount(name) { return this.#events.get(name)?.length ?? 0; }
}

async function parallelLimit(tasks, limit) {
  const results = new Array(tasks.length);
  let index = 0, active = 0;

  return new Promise((resolve, reject) => {
    if (tasks.length === 0) return resolve(results);
    let completed = 0;

    function launch() {
      while (active < limit && index < tasks.length) {
        const i = index++;
        active++;
        tasks[i]().then(res => {
          results[i] = res;
          active--; completed++;
          if (completed === tasks.length) resolve(results);
          else launch();
        }).catch(reject);
      }
    }
    launch();
  });

function deepClone(value, seen = new WeakMap()) {
  if (value === null || typeof value !== "object") return value;     // primitives & functions
  if (seen.has(value)) return seen.get(value);                       // circular reference

  if (value instanceof Date) return new Date(value);
  if (value instanceof RegExp) return new RegExp(value.source, value.flags);

  if (value instanceof Map) {
    const m = new Map(); seen.set(value, m);
    value.forEach((v, k) => m.set(deepClone(k, seen), deepClone(v, seen)));
    return m;
  }
  if (value instanceof Set) {
    const s = new Set(); seen.set(value, s);
    value.forEach(v => s.add(deepClone(v, seen)));
    return s;
  }

  const copy = Array.isArray(value) ? [] : Object.create(Object.getPrototypeOf(value));
  seen.set(value, copy);
  for (const key of Reflect.ownKeys(value)) {
    copy[key] = deepClone(value[key], seen);
  }
  return copy;
}

  memoized.clear = () => cache.clear();
  return memoized;
}

class LRUCache {
  constructor(capacity) { this.capacity = capacity; this.map = new Map(); }
  get(key) {
    if (!this.map.has(key)) return undefined;
    const val = this.map.get(key);
    this.map.delete(key); this.map.set(key, val);
    return val;
  }
  set(key, val) {
    if (this.map.has(key)) this.map.delete(key);
    else if (this.map.size >= this.capacity) this.map.delete(this.map.keys().next().value);
    this.map.set(key, val);
  }
}

function memoizeAsync(fn, ttl = 60_000) {
  const cache = new Map();
  return function (...args) {
    const key = JSON.stringify(args);
    const hit = cache.get(key);
    if (hit && Date.now() - hit.time < ttl) return hit.promise;
    const promise = fn.apply(this, args).catch(err => { cache.delete(key); throw err; });
    cache.set(key, { promise, time: Date.now() });
    return promise;
  };
}

const getProduct = memoizeAsync(id => fetch(`/api/products/${id}`).then(r => r.json()), 30_000);

Concepts: cache invalidation (the hardest part), memory growth (LRU/TTL), key design, only pure functions, caching promises (request dedupe). React Query is a bigger version of this same pattern.

P13Promise.prototype.finally polyfill

Behaviour to replicate:

  • The callback gets no argument.
  • The result is a pass-through: the original value/error moves on (the callback’s return value is ignored).
  • If the callback throws or returns a rejected promise, that becomes the new error.
  • It waits for a promise returned by the callback.
if (!Promise.prototype.finally) {
  Promise.prototype.finally = function (callback) {
    const C = this.constructor || Promise;
    return this.then(
      value => C.resolve(callback()).then(() => value),
      reason => C.resolve(callback()).then(() => { throw reason; })
    );
  };
}

P14retry function

Problem: a network/API call can fail (flaky). When it fails, try again N times with a delay in between (exponential backoff + jitter).

const sleep = ms => new Promise(r => setTimeout(r, ms));

async function retry(fn, { retries = 3, delay = 500, factor = 2, jitter = true,
                           shouldRetry = () => true, onRetry } = {}) {
  let attempt = 0, wait = delay;
  while (true) {
    try {
      return await fn(attempt);
    } catch (err) {
      attempt++;
      if (attempt > retries || !shouldRetry(err)) throw err;
      onRetry?.(err, attempt);
      const sleepFor = jitter ? wait * (0.5 + Math.random() / 2) : wait;
      await sleep(sleepFor);
      wait *= factor;                                             // 500, 1000, 2000...
    }
  }
}

const data = await retry(
  async () => {
    const res = await fetch("/api/payment/status");
    if (!res.ok) { const e = new Error("HTTP " + res.status); e.status = res.status; throw e; }
    return res.json();
  },
  { retries: 4, delay: 400, shouldRetry: e => !e.status || e.status >= 500 }
);

Promise-chain version (when async/await is not allowed in the interview):

function retryPromise(fn, retries) {
  return fn().catch(err => (retries > 0 ? retryPromise(fn, retries - 1) : Promise.reject(err)));
}

Best practices: exponential backoff + jitter (so all clients do not retry together = thundering herd), max retries, retry only idempotent requests (GET) or POST with an idempotency key, AbortSignal for cancel, no retry on 4xx.

console.log(null == 0);          // false
console.log(null >= 0);          // true
console.log(NaN == NaN);         // false
console.log(typeof NaN);         // "number"
console.log("b" + "a" + +"a" + "a");
console.log([10, 9, 1].sort());  // [1, 10, 9]
console.log(["1", "2", "3"].map(parseInt));  // [1, NaN, NaN]
console.log(1 < 2 < 3);          // true
console.log(3 > 2 > 1);          // false

Why (the important ones):

  • 0.1 + 0.2: IEEE 754 binary floating point cannot represent it exactly. Fix: Math.abs(a - b) < Number.EPSILON or calculate in integers (paise).
  • null == 0 is false but null >= 0 is true: in the == rules null equals only undefined; the relational operator >= converts null to 0.
  • +"a" is NaN, so "b" + "a" + NaN + "a".
  • 3 > 2 > 1: (3 > 2) > 1 → true > 1 → 1 > 1 → false.
  • map(parseInt): the callback gives (value, index), so parseInt("2", 1) has an invalid radix 1 → NaN.
  • Real life: do not do money calculations in floating point; use integers (paise) or a decimal library.

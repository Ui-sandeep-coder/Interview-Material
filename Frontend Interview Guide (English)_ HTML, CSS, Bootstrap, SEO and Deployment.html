HTML 18 questions

1What is HTML? Document structure and DOCTYPE

What: HTML (HyperText Markup Language) is the markup language that defines a web page’s structure and content. It is not a programming language; it builds the skeleton of the page with tags/elements (heading, paragraph, image, link, form).

Basic structure:

<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>ShopKart | Online Shopping</title>
  <link rel="stylesheet" href="styles.css">
</head>
<body>
  <h1>Welcome to ShopKart</h1>
  <script src="app.js" defer></script>
</body>
</html>
Part Job
<!DOCTYPE html> Tells the browser this is HTML5 (standards mode). Without it, quirks mode (old buggy rendering rules)
<html lang> The root element; lang helps screen readers and SEO
<head> Metadata: title, meta, CSS links, favicon (not shown on the page)
<body> What the user sees

Element vs Tag vs Attribute: in <a href="/cart">Cart</a>, <a> is the opening tag, </a> the closing tag, href an attribute, and the whole thing an element. Void elements (no closing tag): <img>, <br>, <input>, <meta>, <link>, <hr>. HTML is case-insensitive and forgiving (the browser fixes bad markup), but check with a validator.

2What is Semantic HTML? Why is it important?

What: tags whose name itself tells the meaning (<nav>, <article>) instead of generic <div> / <span>.

<!-- Non-semantic -->
<div class="header"><div class="nav">...</div></div>
<div class="content">...</div>

<!-- Semantic -->
<header>
  <nav aria-label="Main">...</nav>
</header>
<main>
  <article>
    <h1>Running Shoes</h1>
    <section><h2>Reviews</h2>...</section>
  </article>
  <aside>Related products</aside>
</main>
<footer>© 2025 ShopKart</footer>
Tag Meaning
<header>, <footer> Header/footer of the page or a section
<nav> Navigation links
<main> The main content of the page (only one per page)
<section> A thematic group (with a heading)
<article> Self-contained content (a blog post, a product card)
<aside> Side/related content
<figure> + <figcaption> Image/chart + caption
<time datetime>, <mark>, <address> Date, highlight, contact

Benefits: SEO (search engines understand the structure), accessibility (screen readers navigate by landmarks), readability/maintainability, and built-in browser behavior (button, form). Rule: use <button> for a button (not a div + onClick), and you get keyboard, focus, and Enter/Space for free.

6HTML Forms and Validation
<form action="/api/login" method="post" novalidate>
  <label for="email">Email</label>
  <input id="email" name="email" type="email" required autocomplete="email" placeholder="you@example.com">

  <label for="pwd">Password</label>
  <input id="pwd" name="password" type="password" required minlength="8" autocomplete="current-password">

  <label><input type="checkbox" name="remember"> Remember me</label>

  <select name="city"><option value="">Choose city</option><option>Mumbai</option></select>
  <textarea name="note" rows="3" maxlength="200"></textarea>

  <button type="submit">Login</button>
</form>

Important points:

  • <label for> (or put the input inside the label): clicking focuses the input + screen reader support.
  • Without a name attribute the field is not submitted. Use type="button" for non-submit buttons (the default inside a form is submit).
  • Built-in validation: required, minlength, maxlength, min, max, pattern="[0-9]{10}", type=email/url. CSS: :valid, :invalid, :user-invalid. JS: input.checkValidity(), setCustomValidity().
  • GET vs POST: GET puts data in the URL (bookmarkable, cacheable, not for sensitive data, length limit); POST puts it in the body (login, create/update).
  • enctype="multipart/form-data" for file upload.
  • From JS: new FormData(form), e.preventDefault().
  • Client validation is only UX; server-side validation is required.

Types: text, email, password, number, tel, date, time, range, color, file, checkbox, radio, hidden, search, url. <input> vs <button>, and autocomplete tokens for browser autofill.

Best practices:

  • srcset/sizes give the right size per device (a mobile does not download the big image).
  • CDN + compression, a responsive image service.

12iframe and its Security
<iframe src="https://www.youtube.com/embed/xyz" title="Product demo" width="560" height="315"
        loading="lazy" allow="fullscreen" sandbox="allow-scripts allow-same-origin"></iframe>

Use: third-party embeds (YouTube, maps, payment widgets), isolated content.

Risks and defenses:

  • Clickjacking: an attacker puts your site in an iframe and tricks the user into clicking. Defense: the response header X-Frame-Options: DENY or Content-Security-Policy: frame-ancestors 'self'.
  • For untrusted content use sandbox (restricts scripts, forms, popups; manually allow only the permissions needed).
  • The allow attribute controls features (camera, geolocation).
  • To talk to a cross-origin iframe: postMessage (verify the origin).

Downsides: iframe content is not treated as the parent’s for SEO, performance (an extra document), accessibility (give a title), and making it responsive is hard (an aspect-ratio wrapper). Modern alternatives: API integration or Web Components.

14Accessibility (a11y) in HTML: ARIA, keyboard, alt, contrast

Why: users with disabilities (screen reader, keyboard-only, low vision), legal requirements (WCAG, ADA), an SEO bonus, and better UX for everyone.

Rules:

  1. Semantic HTML first (“the first rule of ARIA: if a native element exists, do not use ARIA”).
  2. Keyboard: everything interactive reachable with Tab, a visible focus (:focus-visible), a logical tab order, Enter/Space/Esc behavior, a focus trap in modals, a skip link.
  3. Alt text on images; aria-label on icon-only buttons.
  4. Labels on forms, error messages with aria-describedby, aria-invalid, role="alert" for live errors.
  5. Color contrast: text 4.5:1 (large 3:1) for WCAG AA; do not convey meaning by color alone.
  6. Heading hierarchy (one h1, then h2, h3 without skipping).
  7. A lang attribute, captions/transcripts.
<a class="skip" href="#main">Skip to content</a>
<button aria-label="Close dialog"><svg aria-hidden="true">...</svg></button>
<div role="alert" aria-live="polite" id="msg"></div>
<button aria-expanded="false" aria-controls="menu">Menu</button>
<ul id="menu" hidden>...</ul>
<input id="e" aria-describedby="e-err" aria-invalid="true"><span id="e-err">Enter a valid email</span>

ARIA: role (what it is), aria-* states (aria-expanded, aria-hidden, aria-current="page"), landmarks. Testing: Lighthouse/axe DevTools, the whole flow with only a keyboard, a screen reader (NVDA/VoiceOver), 200% zoom, respect prefers-reduced-motion.

15Browser Rendering Pipeline: DOM, CSSOM, Layout, Paint, Reflow vs Repaint

Critical Rendering Path:

HTML bytes -> Tokens -> DOM tree
CSS bytes  -> CSSOM tree          } -> Render tree (visible nodes + styles; not display:none)
        -> Layout (reflow): position/size nikalna
        -> Paint: pixels bharna (layers)
        -> Composite: combine layers on the GPU
  1. Parse HTML → DOM. A (sync) <script> pauses parsing; CSS can block scripts (the CSSOM is needed).
  2. CSS → CSSOM. CSS is render-blocking.
  3. Render tree = DOM + CSSOM (hidden elements are not included).
  4. Layout (reflow): the geometry of every element.
  5. Paint and Composite.

Reflow vs Repaint:

Reflow (Layout) Repaint
When Geometry changed: width, height, margin, padding, position, font-size, DOM add/remove, window resize Only the look: color, background, visibility, box-shadow
Cost High (the whole/half tree again) Lower
Always a repaint? Yes, after a reflow Without a reflow

Cheapest: transform and opacity (only composite, GPU, no layout/paint).

Avoid layout thrashing: do not mix reads (offsetHeight) and writes (style.width) in a loop. Batch them, requestAnimationFrame, DocumentFragment, toggle classes (instead of inline styles), will-change (carefully).

Optimization: a small CSS at the top, JS with defer, critical CSS inline, image dimensions, a small DOM, animations with transform/opacity.

16What happens when you type a URL in the browser? (a classic question)
  1. URL parse: scheme, host, path. The browser checks cache/HSTS.
  2. DNS lookup: shopkart.com → IP (browser cache → OS cache → resolver → root/TLD/authoritative nameservers). CDN/Geo DNS gives the nearest IP.
  3. TCP connection: 3-way handshake (SYN, SYN-ACK, ACK). (HTTP/3 uses QUIC/UDP.)
  4. TLS handshake (HTTPS): verify the certificate (CA), agree on encryption keys.
  5. HTTP request: GET / HTTP/2 + headers (cookies, accept-encoding).
  6. Server/CDN/Load balancer → app → DB; response status + headers (cache-control) + body (gzip/brotli compressed).
  7. The browser parses HTML: the DOM is built; more requests for CSS/JS/images (the preload scanner finds them in parallel).
  8. CSSOM, render tree, layout, paint, composite (Q15). JS executes (defer/async rules).
  9. The page becomes interactive: DOMContentLoaded, load events, hydration (React).
  10. Later requests: API calls, lazy assets, service worker cache.

Where optimization happens: DNS (preconnect/dns-prefetch), TLS (HTTP/2, session resumption), CDN (latency), compression, caching, the render path (critical CSS), JS (defer/split). When explaining this flow in an interview, mention one optimization at each step.

17Web Components, Custom Elements and Shadow DOM

Web Components: browser-native reusable components (without a framework). 3 technologies: Custom Elements, Shadow DOM, HTML Templates.

<shop-badge count="3"></shop-badge>
<script>
class ShopBadge extends HTMLElement {
  static observedAttributes = ["count"];
  constructor() {
    super();
    this.attachShadow({ mode: "open" });          // Shadow DOM: style/DOM encapsulation
  }
  connectedCallback() { this.render(); }
  attributeChangedCallback() { this.render(); }
  render() {
    this.shadowRoot.innerHTML = `
      <style>span { background: crimson; color: #fff; padding: 2px 8px; border-radius: 99px; }</style>
      <span>${this.getAttribute("count") ?? 0}</span>`;
  }
}
customElements.define("shop-badge", ShopBadge);
</script>

Shadow DOM: the inner CSS does not leak out and outer CSS does not get in (strong encapsulation). To style from outside: CSS custom properties (--color), ::part(), slots (<slot>). Lifecycle: connectedCallback, disconnectedCallback, attributeChangedCallback, adoptedCallback.

Web Components vs React: WC is framework-agnostic and native, while React has a virtual DOM/state/ecosystem. Library: Lit. Useful for design systems that must work across several frameworks.

19What is CSS? Cascade, Inheritance and ways to add CSS

What: CSS (Cascading Style Sheets) controls the presentation of HTML (color, layout, font, animation). Content (HTML) and design are separate.

3 ways:

<p style="color: red">Hi</p>
<!-- 2. Internal -->
<style> p { color: red; } </style>
<link rel="stylesheet" href="styles.css">

(@import is slow, avoid it.)

Cascade (which rule wins): when several rules apply to the same element, the order is:

  1. Importance (!important, origin: user agent < author < user).
  2. Specificity (how specific the selector is).
  3. Source order (the later one wins). (Now @layer is also part of the cascade.)

Inheritance: some properties pass from parent to child (color, font-*, line-height, text-align, visibility, cursor), some do not (margin, padding, border, background, width). Control: inherit, initial, unset, revert.

body { font-family: system-ui, sans-serif; color: #222; }
a { color: inherit; }

CSS syntax: selector { property: value; }. Comments /* */. Shorthand: margin: 10px 20px (top/bottom, left/right), border: 1px solid #ccc, font: 16px/1.5 Arial.

Margin collapsing: adjacent vertical block margins merge into one (the larger): 20px + 30px = 30px, not 50. It also happens between parent and child (if there is no padding/border). To prevent it: display:flow-root, overflow:hidden, padding/border, a flex/grid container (the children inside do not collapse). Horizontal margins do not collapse, not in flex/grid either.

margin: auto centers a block horizontally (with a width). outline takes no space in layout, border does. Vertical margin/padding on inline elements does not affect layout.

24z-index and the Stacking Context

z-index is the order of overlapping elements (higher is on top): only positioned elements (non-static) and flex/grid items.

.modal { position: fixed; z-index: 1000; }

Stacking context: an independent layering group. The z-index of its children is compared only inside the context; the whole context sits at the parent level as one unit.

What creates a new stacking context: the root <html>, position (relative/absolute) + z-index (not auto), position: fixed/sticky, opacity < 1, transform, filter, will-change, isolation: isolate, a flex/grid child with z-index, contain.

<div class="a" style="position:relative; z-index:1">   <!-- context A -->
  <div style="position:absolute; z-index:9999">Child</div>
</div>
<div class="b" style="position:relative; z-index:2">B</div>

Classic bug: a dropdown/modal with z-index: 9999 still does not show because a parent created a new stacking context with transform/opacity. Fix: put the modal near body (a React createPortal), isolation:isolate, a z-index scale (CSS variables: --z-modal: 1000). Painting order: background → negative z → block → float → inline → z-index 0/auto → positive z.

25Flexbox: concepts and properties

What: a 1-dimensional layout (row or column) where items distribute space/align.

.container {
  display: flex;
  flex-direction: row;              /* row | column | row-reverse | column-reverse  (main axis) */
  flex-wrap: wrap;                  /* nowrap (default) | wrap */
  justify-content: space-between;   /* MAIN axis: flex-start | center | space-around | space-evenly */
  align-items: center;              /* CROSS axis: stretch(default) | flex-start | flex-end | baseline */
  align-content: flex-start;
  gap: 16px;
}
.item {
  flex: 1 1 200px;                  /* flex-grow flex-shrink flex-basis */
  align-self: flex-end;
  order: 2;
}

flex: 1 = 1 1 0% (share space equally). flex-grow is the share of extra space, flex-shrink is how much it may shrink (0 = never), flex-basis is the starting size (a higher priority than width/height).

Main vs Cross axis: in row, main = horizontal; in column, main = vertical (justify/align swap).

.nav { display:flex; justify-content:space-between; align-items:center; }
.nav .push-right { margin-left: auto; }
.cards { display:flex; flex-wrap:wrap; gap:16px; }
.cards > * { flex: 1 1 250px; }

Common issues: for item overflow use min-width: 0 (a flex item’s default is min-width: auto, so text overflows), flex-shrink, equal height through align-items: stretch. margin: auto absorbs space inside flex.

43CSS Performance and avoiding CLS (Layout Shift)

CSS performance:

  • CSS is render-blocking: keep the file small, inline the critical CSS (above the fold), and load the rest async (<link rel="preload" as="style" onload="this.rel='stylesheet'">).
  • Remove unused CSS (PurgeCSS, Tailwind JIT, the Chrome Coverage tab), minify (cssnano/Lightning CSS), compress (brotli), HTTP/2 caching.
  • Do not use @import (waterfall), fonts with font-display: swap.
  • Fewer heavy selectors/* and less deep nesting; expensive properties (box-shadow, filter, backdrop-filter) less on big areas.
  • content-visibility: auto (skip offscreen sections), contain: layout paint.
  • Animations: transform/opacity (Q34).

Why CLS (Cumulative Layout Shift) happens and the fix:

Cause Fix
Images/videos without dimensions width/height attributes or aspect-ratio
Late-loading fonts (FOUT) font-display: optional/swap, preload fonts, a size-adjust fallback
Dynamically injected content (ads, banners, cookie bar) Reserve space (min-height), inject from below, overlay
Late CSS Inline the critical CSS
Animations that change layout Use transform

Target: CLS < 0.1. Measure: Lighthouse, the Web Vitals extension, the Chrome Performance panel “Layout Shifts” (Core Web Vitals in the SEO section).

56What is SEO? On-page, Off-page and Technical SEO

What: SEO (Search Engine Optimization) = optimizing a website so it ranks higher in the organic (free) results of search engines like Google and gets more relevant traffic.

A search engine’s work (3 steps): Crawl (discover pages) → Index (store/understand them) → Rank (order them for a query).

Type What Examples
On-page Things inside the page Title, meta description, headings, content quality, keywords, image alt, internal links, URL
Technical The site’s technical health (the frontend developer’s main role) Crawlability, speed, mobile-friendly, HTTPS, sitemap, robots.txt, structured data, Core Web Vitals, rendering (SSR)
Off-page Signals from outside the site Backlinks, brand mentions, social signals, authority
Content/Local Useful content, Google Business Profile Blog, product pages

For a developer: implement technical + on-page. Ranking factors (high level): content relevance/quality, backlinks, page experience (Core Web Vitals), mobile-first, HTTPS, site structure, search-intent match, freshness. White hat vs black hat: keyword stuffing, hidden text, link farms, cloaking = penalty. SEO takes time (weeks to months); SEM/paid ads give instant but paid results.

60The SPA/React SEO problem: CSR vs SSR vs SSG vs ISR

Problem: with CSR (Client-Side Rendering) a React app’s initial HTML is empty (<div id="root"></div>), and content appears after JS runs. Google can render JS (a second wave, with delay and resource limits), but other crawlers/social bots (WhatsApp, Facebook, Twitter, partly Bing) do not run JS → bad previews/indexing; slow LCP.

CSR SSR SSG ISR
When HTML is made In the browser On the server for every request At build time Build + background regeneration
SEO Weak Strong Strong Strong
Speed (TTFB) Fast shell, slow content Depends on the server Fastest (CDN) Fast
Fresh data Yes Yes Stale until rebuild Fresh at intervals
Use Dashboards, logged-in apps Dynamic product/search pages Blogs, docs, marketing Product catalogs (lakhs of pages)

Solutions:

  1. Next.js (a React framework): SSR/SSG/ISR, the metadata API, image optimization, sitemap/robots support.
  2. Remix / Gatsby / Astro, and Nuxt for Vue.
  3. Prerendering (prerender.io, react-snap) for static pages; dynamic rendering (prerendered HTML for bots): Google no longer recommends it.
  4. Dynamic meta tags (Q61).

62Core Web Vitals: LCP, INP, CLS (and how to improve them)

Google’s page experience metrics (a ranking signal; real-user data: CrUX). They must be “Good” at the 75th percentile.

Metric Meaning Good How to improve
LCP (Largest Contentful Paint) When the largest content (hero image/heading) appeared <= 2.5s Optimize the hero image (WebP/AVIF, fetchpriority="high", preload, CDN), a fast server/TTFB (SSR/cache), less render-blocking CSS/JS, preload fonts, do not lazy-load the hero
INP (Interaction to Next Paint) (replaced FID) How fast the UI responds after a click/tap/key <= 200ms Break long tasks (>50ms), less JS/split, useTransition, heavy work in a Web Worker, light event handlers, defer third-party scripts
CLS (Cumulative Layout Shift) How much the layout moved <= 0.1 Image/video dimensions, space for ads/embeds, font swap handling, animations with transform

Supporting metrics: TTFB (server response, <800ms), FCP, TBT (a lab proxy for INP), Speed Index.

64URL Structure, Redirects (301 vs 302), Canonical, 404 and Pagination

URL best practices: short, readable, lowercase, hyphens, keywords, no session IDs/many params, HTTPS, a consistent trailing slash, one choice of www vs non-www.

Good:  https://shopkart.com/men/running-shoes
Bad:   https://shopkart.com/index.php?cat=12&id=9983&sess=ab12

Redirects:

Code Meaning SEO
301 Permanently moved Link equity (ranking) passes to the new URL
302 / 307 Temporary The original URL stays in the index
308 Permanent, preserves the method

Use: domain/URL change, http→https, www→non-www, old pages. Avoid redirect chains/loops (301 → 301 → 301 is slow + crawl waste). Server level (Nginx return 301), CDN, framework config, or React Router <Navigate> (a client redirect, weak for SEO).

Canonical: rel="canonical" points to the preferred URL for duplicate/near-duplicate URLs (?utm=, filters, /product vs /product/).

404 vs soft 404: a missing page needs a real 404 status (200 + “not found” text = a soft 404, junk in the index). A custom 404 page with helpful links. Permanently removed = 410. The SPA problem: the client router shows “not found” but the server returns 200; give the right status from SSR/the server.

Pagination: crawlable <a href> links like ?page=2, a self-canonical (do not point to page 1), real links even with “Load more”. For infinite scroll, a fallback of paginated URLs. Control faceted filters with noindex/robots.

65Image SEO, International SEO (hreflang) and Mobile-first Indexing

Image SEO: descriptive alt, a meaningful file name, WebP/AVIF + compression, responsive srcset, width/height, lazy load (not the hero), an image sitemap, structured-data images, relevant surrounding text.

International SEO:

<link rel="alternate" hreflang="en-in" href="https://shopkart.com/en-in/">

Mobile-first indexing: Google now mostly crawls/indexes the mobile version. So: Responsive design (best), the same content/structured data/meta on mobile and desktop, the viewport meta, tap targets, no intrusive interstitials, mobile speed, lazy-loaded content that is crawlable (Intersection Observer, <a> links), and do not block CSS/JS in robots.txt.

69Frontend Environment Variables (and the truth about secrets)

Problem: dev, staging and production need different API URLs/config.

# .env.development
VITE_API_URL=http://localhost:5000/api
# .env.production
VITE_API_URL=https://api.shopkart.com

const api = import.meta.env.VITE_API_URL;

How it works: variables are text-replaced (inlined) into the code at build time. That means: you cannot change them at runtime (you cannot run the same build in dev and prod; rebuild per env, or use a runtime config.json).

Most important: frontend env variables are PUBLIC. Anyone can see the bundled JS in the browser. Never put secrets (API secret keys, DB passwords, private tokens) in frontend env; go through a backend/serverless proxy. Only public keys (a Google Maps key restricted by domain, Stripe’s publishable key).

Best practices: do not commit .env to Git (.gitignore), commit a .env.example, set env in CI/CD/the host dashboard (Netlify/Vercel/GitHub secrets), runtime config through public/config.js or window.__ENV__ (one Docker image, different env), prefix discipline, validate on startup.

71Deploying a React App on AWS S3 + CloudFront (step by step)

Architecture: Route 53 -> CloudFront (HTTPS, CDN, cache) -> S3 (private bucket, static files).

Steps:

  1. npm run build → dist/.
  2. Create an S3 bucket (Block Public Access ON, private).
  3. A CloudFront distribution: the origin is S3 with OAC (Origin Access Control) (only CloudFront can read the bucket). The default root object is index.html. Viewer protocol: redirect HTTP to HTTPS.
  4. SPA routing: CloudFront custom error responses: 403 and 404 → /index.html, HTTP 200.
  5. SSL certificate: ACM (in us-east-1 for CloudFront), a custom domain (alternate domain name CNAME) + a Route 53 alias record.
  6. Upload:
aws s3 sync dist/ s3://shopkart-web --delete \
  --cache-control "public,max-age=31536000,immutable" --exclude "index.html"
aws s3 cp dist/index.html s3://shopkart-web/index.html --cache-control "no-cache"
aws cloudfront create-invalidation --distribution-id E123ABC --paths "/index.html"

Caching logic: hashed assets (app.3f9a.js) get 1 year immutable, index.html gets no-cache (so a new deploy shows up immediately). Keep old assets for a while for users’ open tabs (do not delete immediately). Automation: GitHub Actions + an OIDC role (Q73), IaC (Terraform/CDK). Alternative: AWS Amplify Hosting (Netlify-like, Git integrated). Security headers: a CloudFront response headers policy (HSTS, CSP).

75Caching Strategy and CDN (for frontend deployment)

Golden rule:

File Cache-Control Why
index.html no-cache (validate with the server every time) A new deploy shows immediately
assets/app.[hash].js/css public, max-age=31536000, immutable The hash changes when the content changes
Images/fonts (hashed) Long cache
API responses Depends on the app (private, no-store, or short)

The cache-busting problem: if app.js (without a hash) is cached for 1 year, users see old code. That is why content-hash filenames (the bundler does it).

CDN benefits: served from the edge near the user (lower latency), less origin load, DDoS protection, compression/HTTP2/3, image optimization. Invalidation: index.html (and others if needed) invalidate/no-cache.

Service worker cache (PWA): cache-first assets, network-first API; the stale app version problem: when a new SW activates, show an update prompt (“New version available - Refresh”).

Stale chunk error: after a new deploy, an old tab asks for a lazy chunk (Dashboard.abc.js) that is no longer on the server (404) → “ChunkLoadError”. Fix: keep old assets for a while, a page-reload prompt on error, a version check, an Error Boundary. ETag/Last-Modified conditional requests (304).

76Dev Proxy vs Production API URL and CORS

Development: the frontend is localhost:5173, the backend localhost:5000 → different origins → a CORS error.

Solution 1: a dev proxy (the browser thinks it is the same origin):

In the code just use fetch("/api/products") (a relative URL).

  1. A reverse proxy (best): Nginx/CloudFront on one domain: / → static, /api/* → backend. No CORS needed, simpler cookies.
  2. A separate domain (api.shopkart.com): CORS config on the backend (allowed origin, credentials), cookies SameSite=None; Secure or a same-site subdomain, fetch(..., { credentials: "include" }).

  • “No Access-Control-Allow-Origin” → the backend CORS config (not a frontend fix).
  • A failing preflight (OPTIONS) → allowed headers/methods.

80PWA and Service Workers

PWA (Progressive Web App): a web app that feels like a native app: installable, offline-capable, fast, with push notifications. Requirements: HTTPS, a Web App Manifest, a Service Worker.

// manifest.webmanifest
{ "name": "ShopKart", "short_name": "ShopKart", "start_url": "/", "display": "standalone",
  "background_color": "#ffffff", "theme_color": "#0b7285",
  "icons": [{ "src": "/icons/192.png", "sizes": "192x192", "type": "image/png" },
            { "src": "/icons/512.png", "sizes": "512x512", "type": "image/png", "purpose": "maskable" }] }

Service Worker: a background script between the browser and the network (a separate thread, no DOM access, intercepts requests like a proxy).

// register (main.js)
if ("serviceWorker" in navigator) navigator.serviceWorker.register("/sw.js");

// sw.js
const CACHE = "shopkart-v3";
self.addEventListener("install", e => {                         // precache app shell
  e.waitUntil(caches.open(CACHE).then(c => c.addAll(["/", "/offline.html", "/assets/app.js"])));
  self.skipWaiting();
});
self.addEventListener("activate", e => {                        // purane caches saaf
  e.waitUntil(caches.keys().then(keys => Promise.all(keys.filter(k => k !== CACHE).map(k => caches.delete(k)))));
});
self.addEventListener("fetch", e => {
  if (e.request.method !== "GET") return;
  e.respondWith(                                                // cache-first, fallback network, fallback offline page
    caches.match(e.request).then(hit => hit ?? fetch(e.request).catch(() => caches.match("/offline.html")))
  );
});

Lifecycle: register → install → (waiting) → activate → fetch/push/sync events. Caching strategies: Cache-first (static assets), Network-first (API/HTML), Stale-while-revalidate (balance), Network-only, Cache-only. Workbox (a Google library) makes it easy. Features: background sync, push notifications (Push API + Notifications), add to home screen. Pitfalls: stale cache/update flow (a new SW is “waiting”; prompt the user), HTTPS only, scope (/sw.js at the root), debugging (the DevTools Application tab). Vite: vite-plugin-pwa.

82Web Fonts: loading, FOIT/FOUT and optimization

Problem: when a custom font loads late, the text is invisible (FOIT) or swaps from a fallback (FOUT), causing flicker and CLS/LCP issues.

@font-face {
  font-family: "Inter";
  src: url("/fonts/inter-var.woff2") format("woff2");
  font-weight: 100 900;                  /* variable font: ek file, sab weights */
  font-display: swap;
  unicode-range: U+0000-00FF;            /* subset */
}
body { font-family: "Inter", system-ui, -apple-system, "Segoe UI", sans-serif; }
font-display Behavior
block Hidden text (up to 3s) then the font
swap Fallback immediately, swap later (FOUT)
fallback A short block period, limited swap
optional The font only if it arrives quickly, otherwise stay on the fallback (zero CLS)

Optimization:

  1. The woff2 format (best compression).
  2. Preload the critical font: <link rel="preload" href="/fonts/inter.woff2" as="font" type="font/woff2" crossorigin> (crossorigin is required).
  3. Subset (only the needed glyphs/languages), variable fonts.
  4. Self-host (better than an external Google Fonts request; or preconnect to fonts.gstatic.com).
  5. Fewer families/weights.
  6. size-adjust/ascent-override to size-match the fallback font to the custom one (less CLS).
  7. A system font stack if the brand font is not essential.

Google Fonts: <link rel="preconnect" href="https://fonts.googleapis.com"> + &display=swap in the URL. Use inline SVG instead of icon fonts (FontAwesome) (lighter, a11y).

      setItems(prev => [...prev, ...d.items]); setHasMore(d.hasMore);
    });

}

89Tricky HTML/CSS Output Questions

1. Margin collapse:

<div style="margin-bottom: 20px">A</div>
<div style="margin-top: 30px">B</div>

The gap = 30px (collapse, the larger margin), not 50.

2. Specificity:

#a .b { color: red; }  .a.b.c.d.e.f.g.h.i.j.k { color: blue; }

The text is red (the ID column always wins).

3. em compounding:

div { font-size: 2em; }   /* <div><div><div>text</div></div></div> */

The innermost div’s size is 16 x 2 x 2 x 2 = 128px.

4. Width 100% + padding:

.box { width: 100%; padding: 20px; }          /* content-box: overflow! (100% + 40px) */

Fix: box-sizing: border-box.

5. position: absolute without a positioned parent: relative to the page/viewport (the initial containing block). 6. A float parent has height 0 (clearfix). 7. z-index does not work (on a static element, or in a different stacking context).

8. width/height on an inline element: no effect. 9. visibility:hidden vs display:none (space). 10. 100vh on mobile overflows because of the address bar → dvh.

11. Flex item overflow:

.row { display: flex; } .row > p { white-space: nowrap; }     /* text overflow */

Fix: min-width: 0 + overflow: hidden; text-overflow: ellipsis.

12. Center a div (Q28), 13. :nth-child(2n+1) = odd, :first-child vs :first-of-type.

14. <br> vs margin, 15. !important vs an inline style: an !important rule beats a normal inline style.

16. Why must a:hover come after a:visited? The LVHA order (Link, Visited, Hover, Active): when specificity is the same, the later rule wins.

17. What is the output?

<p>Hello <span style="display:none">hidden</span> World</p>   <!-- "Hello  World" (extra space collapse -> ek space) -->

Multiple whitespace in HTML becomes one space (stop it with white-space: pre, or &nbsp;).

18. <button> vs <input type="button">: you can put HTML inside a button. 19. The position of <script>, the blocking of <link>. 20. A duplicate id → getElementById returns the first element (invalid HTML).
